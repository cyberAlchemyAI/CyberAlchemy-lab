# Candidate proof submission verification

R02 checks an actual submitted theorem against an independently selected required statement. It does not aggregate extension readiness. The supported theorem catalog covers registry preservation and conservativity, independent F0 root meaning, a captured rule profile, derivation soundness, closure adequacy, protected lineage, countermodel soundness and rule conservativity.

The public entrypoint is `proof-replay-runner SUBMISSION --proposal PROPOSAL`. Its JSON submission is a local successor to the draft interface, identified by `relational.proof-submission/v1-candidate`; draft contracts remain historical candidate artifacts. The proposal is an input, not a caller-selected statement policy. The independently generated obligation ID selects the required declaration and exact statement mode. Generic proposition aliases use their definition value, which is the quantified proposition, rather than their type `Prop`. Concrete obligations use the type of a freshly generated trusted theorem.

The request binds its source file, theorem identity, proposal, policy, complete dependency manifest and semantic statement identity. `make_submission` supplies these transport fields from current trusted policy. A client may supply a new Lean proof body; verification is not a whitelist of known theorem bodies. Changing a rule version, source declaration, required type or dependency bytes invalidates the previous request. A generic lemma rechecked under a new context may remain valid, but an old receipt cannot be transplanted to that context.

The runner fresh-compiles the trusted source modules in a private build. Submitted elaboration runs in a Bubblewrap namespace with cleared environment, isolated network and read-only toolchain/source/trusted-driver mounts. Its writable scratch is a sized tmpfs. A bounded archive transports compiled bytes back; archive entries, compiler messages and operational success are untrusted. No writable host directory is mounted.

A second isolated process runs `Verifier.lean`. It checks the compiled module's imports and declaration ownership, loads data with submitted extensions and initializers disabled, compares the required semantic definitions and allowed-axiom types with a separately loaded trusted environment, and traverses the actual proof's transitive dependencies. It replays the pure proof/type dependency closure into an empty Lean kernel and adds a new declaration whose value is the submitted theorem and whose type is the trusted required proposition. This is an independent checking path using the same pinned Lean kernel, not a separately implemented kernel.

`audit_text` is a low-level control-test helper whose caller supplies the trusted environment. Its raw report is not a public currentness-bound submission receipt. Public evidence must pass `check` or the runner, which validates complete bindings before and after execution. R03 must independently verify the complete obligation set and actual extension hypotheses or witnesses. For example, proving countermodel-checker soundness does not establish that the proposed countermodel passes that checker.

The trust boundary includes the pinned Lean kernel and binary-data parser, the verifier and host projections, Python and OS/namespace correctness, the hash function, and source interpretation. Independent assessment truth remains a supplied assumption. Address-space and CPU limits apply per process; process/thread limits apply through the OS user accounting. This candidate does not claim aggregate cgroup quotas or production multi-tenant denial-of-service isolation. Unsupported source-wide semantics remain visible; no authority admission or live deployment occurs here.

Run `python3 run_verifier.py` from this directory, or invoke it by its repository path, to fresh-build the trusted modules, audit every catalog family, exercise hostile compiled statements independently of lexical filtering, probe isolation, and replay a full public submission. `submission-controls.json` records actual results. A failed elaboration or type/axiom check rejects the proof; timeout or missing isolation yields unknown/unavailable with no proof acceptance.

The frozen trusted theorem modules use Lean's legacy module mode. Lean rejects importing those modules from a `module`-mode source. The transport and audit still inspect exported/server/private compiled parts when present; handling those bytes does not widen the supported import profile.
