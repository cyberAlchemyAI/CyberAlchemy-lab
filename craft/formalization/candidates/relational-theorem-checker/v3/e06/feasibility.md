# Independent-checker feasibility review

An independent checking path is feasible for an actual closed sample. The standalone Rust nanoda checker accepted E00's unknown-preservation theorem and its complete 18-declaration export, with zero permitted axioms and no native-evaluation/Nat/String extensions. This is a measured sample, not independent assurance of the whole relational checker. The original same-kernel path remains mandatory.

Official Lean documentation distinguishes stored-proof replay from external checking and recommends comparing a proof with an independently anchored challenge. That motivates retaining both exact statement/definition identity and a separately implemented checker. [Proof validation documentation](https://lean-lang.org/doc/reference/latest/ValidatingProofs/). The actual exported sample preserves universes, dependent binders, equality, finite Truth constructors, PUnit, recursors, definitions and proof terms; `dependency-closure.json` lists the full groups and instances.

The study considered Lean4Lean and nanoda. Lean4Lean's own README describes its checker as derived directly from the C++ kernel and cautions that this can share implementation bugs; it is useful for cross-checking but algorithmic independence is a separate property. [Lean4Lean source](https://github.com/digama0/lean4lean). Nanoda is implemented in Rust and ran as a standalone binary here. Its pinned source and Cargo lock/build products are recorded in `tools.lock.json`; pinning does not constitute verification of that implementation.

Actual controls checked the positive proof, forged original acceptance bit with an invalid proof, dropped universe instance, unpermitted axiom, changed statement, missing inductive dependency and a valid proof under a substituted definition. The last case illustrates the specification boundary: a checker can correctly validate a theorem with the wrong meanings. Structural challenge comparison and an exact original closure pin reject that substitution. See `sample-check-report.json` for exact inputs, outputs, exits and per-check times; all controls passed.

The Rust release build took 3 minutes 25 seconds in the recorded build log. The exporter generated compatible Lean modules, but native C compilation failed because the local pinned cache lacks headers; the interpreted exporter succeeded without installing or changing the core kernel. The independent positive sample took milliseconds, which cannot predict full-core throughput. Export size, theorem closure, recursive definitions, universes, axiom policy, format/toolchain compatibility and adversarial regressions determine broader cost.

A full implementation must export and independently compare every theorem's actual statement and complete referenced definitions, handle the full core's foundational axioms/recursors/quotients and large certificates, enforce owned resource limits, and make checker disagreement/refusal explicit. This study does not prove that integration. No required core unit depends on E06 and no sample result enables application or publication.

The pinned 4.33.1 release already documents the relevant runtime/kernel/GMP backports; the newer 4.34 release notes repeat these, so the release-number difference alone is not evidence that this pin lacks those fixes. Those notes also describe an issue shared by Lean and nanoda, reinforcing that independent implementations do not eliminate all shared assumptions. [Pinned release notes](https://lean-lang.org/doc/reference/latest/releases/v4.33.1/). No toolchain upgrade or broad security claim was inferred.
