DomainSpec v2
User Guide

A game team begins with a simple idea: a player with the right key can unlock a door. The idea sounds complete until the team asks what counts as the right key, what allows the unlock, what changes, and what gets recorded.

What is DomainSpec?

Different people may answer those questions differently. DomainSpec calls the part of the game they are describing—the player, key, door, and rules around unlocking—the domain. It gives the team a shared way to name its parts, record the roles they play, explain how they relate, and state the rules the implementation must respect.

From that description, the team can make implementation obligations explicit, derive test material from supported declarations, connect results to code evidence, and state precisely what each result proves.

DomainSpec is the system that supports this process. A DomainSpec specification is the description the team creates. DomainSpec is not the game or its application framework, and it does not decide whether the feature is correct.

  1. Shared specification
  2. Obligations
  3. Derived test material
  4. Code evidence
  5. Bounded proof

Proof has a precise limit here. It says what named inputs, checks, and results support. It does not prove the whole game, approve the implementation, or authorize a release.

Today these stages are not one finished path. The selected JSON authoring route and the current test-derivation route remain separate, and architecture enforcement is still candidate and partial.

DomainSpec works like grammar for a system description

A language is easier to share when it has known words, roles, and sentence patterns. DomainSpec does a similar job for a system description.

Concepts are the vocabularyThe named parts of the feature.
Meta-types are the rolesWhat job each named part performs in the description.
Relationships are the verbsHow two parts connect, including direction.
The graph is the sentence mapIt shows who connects to what, and in which direction.

Where the analogy stops

A grammar checker can find a malformed sentence, but it cannot prove the sentence is true. In the same way, DomainSpec can reject some malformed descriptions; it cannot by itself prove the business meaning or the running software.

DomainSpec helps a team make feature decisions explicit and carry them toward checks and evidence. It does not build the feature or decide whether the feature is correct.

That is the feature we will follow. The request below captures the team’s starting point. From there, we’ll make each decision with them and see how DomainSpec gives every part of the mechanic a clear place.

01 · The problem

A key, a door, and four questions

A player with the right key should unlock a door. Everyone understands that sentence—until the team must agree on exactly what the rule, action, and result are.

“A player with the right key unlocks the door.”

The sentence sounds complete. It is not yet precise enough for different people—or different tools—to interpret in the same way.

The hidden decisions

  • 1
    Which thing keeps its identity?
  • 2
    Which thing decides yes or no?
  • 3
    Which action changes the system?
  • 4
    What records that the change happened?

What DomainSpec adds

DomainSpec gives the team a shared way to answer those questions, connect the answers, and check whether the description follows the selected structural rules.

What stays with people

The team still decides whether the description means the right thing. A structural check does not prove that the running game behaves correctly.

If the profile cannot express your concept

Do not invent a new kind, improvise a body for one of the other nine active backend types, or use a relationship outside the current three. 05 · Describe one part of the system

Turn one team decision into a concept

The team has decided that an unlock attempt is allowed only when the player holds the required key. That decision now needs a stable place in the project so everyone can name it, connect it to the unlock action, and review the same meaning later.

What DomainSpec calls a concept A concept is one named part of the system description. Here, HasKeyRule is the team’s name for the decision that allows or blocks UnlockDoor.

Answer six questions

The questions begin with the team’s meaning. Their answers become the fields of one source record.

QuestionThe team’s answerWhere it goes
What does this decision mean?Allow unlocking only when the player holds the required key.intent
What job does it perform?It returns a yes-or-no decision that allows or blocks an action.kind: Rule
Which feature owns it?Key & Door.feature_id: key-and-door
What is its stable name?HasKeyRule inside that feature.node_id: key-and-door.HasKeyRule
What must every Rule state?Its formal result is boolean: yes or no.body.formal_return_type
What does it govern?The UnlockDoor action.enforces → key-and-door.UnlockDoor

Assemble the answers into one source node

The checked Key & Door fixture stores those answers in nodes/has-key-rule.json:

{
  "schema_version": "minted-node/v1",
  "node_id": "key-and-door.HasKeyRule",
  "feature_id": "key-and-door",
  "kind": "Rule",
  "intent": "Allow the unlock operation only when the player holds the key.",
  "body": { "formal_return_type": "boolean" },
  "connections": [{
    "edge_id": "key-and-door.edge.has-key-rule-enforces-unlock-door",
    "type": "enforces",
    "to": "key-and-door.UnlockDoor"
  }]
}

What the current check can establish

Under the selected experimental profile, a check can confirm that this record has the required Rule body and that a Rule may enforce an Operation.

It cannot decide whether the rule expresses the right game design, inspect the game’s code, or prove that the player is blocked at runtime.

Where this node belongs

This record is not a complete project. It belongs beside project.json, the Key & Door feature record, and every node it references—including UnlockDoor.

08 · Change the language

When the existing types are not enough

Most projects should never need a new meta-type. A meta-type changes the vocabulary available to every specification, so a new label begins as a question—not as an official type.

A new concept uses the language

HasKeyRule belongs to one project and uses the existing Rule meta-type.

Create another concept when the project needs another named Rule, Operation, Entity, or other supported kind.

A new meta-type changes the language

A meta-type defines a role that many projects may use. It changes what declarations count as well formed, which connections they may make, and which later checks can distinguish them.

That change needs evidence and a definitions-owner decision; one feature cannot approve it for everyone.

Try to disprove the proposal first If an active type plus its properties and relationships preserves the distinction, stop. A different framework word, class name, or diagram label is not enough. The proposal must change a check or another tracked result.

Follow a real proposal: should Page be different from Component?

A product team keeps describing InventoryPage and MapPage as Components. It proposes Page as a separate role because a Page owns a destination: a route, primary content, layout, access context, and the units placed on it. A reusable Component does not own a route.

That difference is promising, but it is still a candidate. The current Page evidence has not yet been reproduced independently across route frameworks, so Page is not active or promotion-ready.

Author the candidate as a question the evidence can answer

Phase 1

Show where the language fails

Try the active types first. Then name the exact failure and compare the closest neighbour.

For Page, the question is whether a routeless Component could wrongly satisfy the description of a terminal destination. Page owns the destination; Component does not.

Phase 2

Make the difference testable

Write the separating formation rule, place the candidate in one category, and propose its incoming and outgoing relationship roles.

Test a valid Page, a deliberately invalid neighbour, and at least one real project example. Record the exact check or tracked result that changes.

Phase 3

Submit evidence, not a verdict

The human card, candidate schema, fixtures, automated tests, and known limitations form a review packet. They do not allocate an official ID or choose a permanent file home.

The definitions owner decides maturity. Even activation does not add the type to every source profile or approve a code form, release, or production use.

09 · From description to evidence

Turn a specification into checks—and compare code with it

The Key & Door description says that HasKeyRule gates UnlockDoor. The next questions are different: what must eventually be checked, and what should the code preserve?

First: make the checklist

The Test Derivation Engine turns supported declarations into stable obligations: small, named items that later tests or implementation evidence must account for.

It does not invent missing behavior, generate the application, or decide whether the business meaning is right.

Then: inspect the code shape

Architecture type enforcement compares selected expectations for a DomainSpec type with facts gathered from exact code. The repository calls the wider program Architecture-Pattern Enforcement.

It reports matches, differences, missing evidence, and unsupported cases. It does not approve the implementation.

From one description to a decision the evidence can support

  1. Source description
    Names the concepts, their roles, and their connections
  2. Obligations
    The checklist maker names what must be accounted for
  3. Architecture expectations
    A selected mapping and profile say what the code should preserve
  4. Exact code target
    An evidence collector inspects named code and tools
  5. Observed facts
    The collector reports what it actually found
  6. Findings and receipt
    Expected and observed facts are compared with their limits
  7. Owner decision
    A responsible person decides what the evidence permits next
Which parts work today?
  • The selected JSON path can build and verify the Key & Door graph, source manifest, Markdown view, and build receipt.
  • The Test Derivation Engine can turn legacy aspect documents or an explicit normalized SPEC.md into obligations and test material. Supported bindings and formal expressions can produce real assertions; unsupported behavior remains a visible gap.
  • A narrower JSON-to-node-logic projection exists for explicitly admitted logic-bearing nodes. It is not the general test bridge for the four-kind Key & Door profile.
  • The direct selected-JSON-to-obligations path for this guide remains planned. It must use verified machine views rather than treating generated Markdown as new source.
  • Limited local architecture checks exist for selected types and one Rule enforces Operation composition. Wider type coverage, profiles, adapters, integration, and release evidence remain partial.

Architecture type enforcement in plain language

A DomainSpec type can look different in TypeScript, Python, and Rust while keeping the same meaning. Architecture enforcement separates what must remain true everywhere from conventions that belong to one language or project.

The terms name different jobs. An obligation names something that must be accounted for. An architecture mapping proposes how a type may appear in code. A profile lists selected expectations. A provider gathers facts from the exact target. A finding explains a match or difference. A receipt records the inputs, results, and limits.

Rule

It must still make a true/false decision, even though each language writes the callable differently.

Enum

It must keep the same owned list of values, even when languages use different enum syntax.

Value Object

Equality must still use every owned field and values must stay immutable; hash bytes may differ by language.

How the code-shape inspector records what it checked

  1. Requestnames the checks and repository inputs
  2. Dependenciesproviders list every file and tool they need
  3. Planlocks the exact files and tool versions
  4. Runuses copied inputs and checked references
  5. Replayrepeats each check in a separate process
  6. Verifyseparates the relevant result from machine-only details
  7. Recordwrites the result only after verification

A repeatability check compares two isolated copies. inspect and init stop instead of guessing when a code mapping is still only a proposal, a type is not active, a referenced file has changed or is missing, or an identifier is invalid. There is no shortcut around these checks.

Where the two mechanisms meet—and where they stop

The intended join

Derived obligations say what needs evidence. Architecture expectations say what the implementation should preserve. Observations and findings show what one exact code target actually supports.

specification

The current gap

These pieces are not one supported end-to-end path for the selected Key & Door JSON profile yet. The current derivation input and the selected authoring input remain separate, and architecture enforcement is candidate and partial.

Generated tests are not test executions. Passing tests and receipts are evidence, not implementation acceptance or release authorization. Experimental architecture.* connections also cannot redefine DomainSpec’s domain relationships.

11 · Product boundary

What it owns—and where it stops

Different files and tools answer different questions. Keeping those responsibilities separate prevents a test or generated file from approving something it cannot approve.

DomainSpec v2 is

  • A defined set of concept types.
  • Rules that check what each type must contain.
  • A list of allowed connections between types.
  • A JSON compiler that builds verified views, plus a separate legacy engine that generates structural checks from Markdown.
  • Experiments that compare the design with code evidence.
  • A private project whose decisions apply inside this repository.

DomainSpec v2 is not

  • A general-purpose programming language.
  • A proof that a written description is true in the real world.
  • An LLM that guesses meaning.
  • A universal tool that turns requirements into an application.
  • A claim that all meta-types are implemented.
  • The Saturn control loop or a shipped public product.

Place in the wider private system

What

DomainSpec

What the system is meant to contain and mean, plus the checks that follow from that description.

How

Arcanum

Reusable ways for people and agents to perform controlled work. This is the public pillar.

Loop

Saturn

The separate private loop that compares the design with observed reality and routes corrections.

Private/public boundary. DomainSpec and Saturn are not publicly shipped. The wider-system documents are private drafts for orientation; they do not define DomainSpec v2.

Who owns which part?

DomainSpec defines and checks

  • The shared definitions, type labels, and required information for each type.
  • The allowed DS-D8 connections and their endpoint types.
  • Consistent maps, generated views, and focused structural checks.
  • Methods for validating the description and reporting disagreements between sources.

Other sources and owners decide

  • The project's business meaning.
  • What the running code and language tools actually do.
  • Implementation acceptance.
  • Release, deployment, and production satisfaction.

Definitions

Define the shared language and its required shapes. They cannot claim production behavior.

Project source

Defines what a feature means. Using DomainSpec does not let a project redefine the shared language.

Validators

Report whether one exact check passed or failed. A pass is evidence for that check, not proof of the whole application.

Generated views

Make maps and reports easier to read. They are not the source people edit.

Implementation experiment

Describes expected code properties and observed differences. It cannot approve a DS-D1 definition.

Responsible owner

Decides whether an implementation, release, deployment, or production use is accepted.

12 · Keep status questions separate

A type can be defined without being implemented—or ready

A single “complete” badge would hide important gaps. Ask these six questions separately.

1 · Can the type be used?active · candidate · deferred · superseded

2 · Is there a proposed code form?candidate-mapped (proposed) · not-admitted (not formally accepted) · superseded (replaced)

14 · Limits and troubleshooting

Claims and setup assumptions to challenge

Most mistakes happen when evidence from one step is treated as proof of a different step.

“The class name says Entity.”

The declared fields and identity rule make it an Entity, not a class suffix or framework decorator.

“The code returns boolean, so the concept is a Rule.”

The DomainSpec source must declare formal_return_type = boolean. What a tool sees in code cannot rewrite the intended meaning.

“A generated test passed, so the application is correct.”

Only that exact check passed on the recorded inputs. It does not prove the application's full behavior or business correctness.

“Candidate-mapped means the code-checking process is ready.”

It means only that a possible code representation has been proposed. The process still needs an approved mapping, language rules, a tool that inspects code, sufficient evidence, readiness, and owner approval.

“Every connection needs a relationship.”

Imports, reverse navigation, and diagram convenience often belong in metadata or generated views.

“An active UI verb makes Page or Guard active.”

The connection's status and each endpoint type's status are separate. The UI labels remain non-active.

“Generated Markdown is the source.”

In the selected consumer path, edit project.json, the feature record, or a node record and rebuild. In the separate legacy path, edit the explicit legacy input. Never repair a generated Markdown view by hand.

“Saga is available because it is no longer active.”

DS-D1.10 is a permanently retired historical ID. Use Workflow and never reuse the number.

Current repository troubleshooting

npx --no-install cannot find tsx

The checkout is not prepared. This guide does not yet have an approved clean-install procedure. Ask the maintainer for the supported setup rather than silently downloading a different tool.

pnpm reports ERR_PNPM_IGNORED_BUILDS

The current workspace leaves the esbuild allowBuilds decision unresolved. Dependency build permission belongs to the setup owner; do not approve scripts blindly.

Legacy content validation passes but engine lint fails

These Markdown checks cover different boundaries. On 2026-08-13, Financial Settlement passed broad content and connection checks but engine lint found one non-canonical graph table. This says nothing about a minted JSON package. Use Agent Execution Orchestrator when you need a parser-clean legacy example.

The receipt contains parser rejections

A receipt records accepted, omitted, and rejected inputs. Run lint first and inspect summary.parser_rejections; receipt creation is not semantic approval.

npm run validate passed

The script does not run every engine test, typecheck, tag, instance, factory, experiment, browser, release, or production check. Report the exact command that passed.

15 · Evolve carefully

How to extend DomainSpec responsibly

Add a type or connection only when an existing one cannot express an important distinction, and show exactly which check or generated result would change. Writing a required-shape file or an experimental code-mapping record does not make the proposal approved.

Add a concept

Use an active type, add its required information and allowed connections, then check both the concept and graph.

Propose a meta-type

Follow the candidate meta-type path: disprove the need first, separate the nearest neighbour, add discriminating evidence, and preserve the definitions-owner gate.

Add a relationship

Define endpoint types, direction, quantity limits, location, examples, invalid cases, and what validation or output changes without it.

Add a code form

Keep the shared meaning with the type's owner and executable code observations with the owner of the code being inspected.

Add a code evidence collector

List the exact inputs, tools, dependencies, generated checks, deliberately wrong cases, reruns, file-change checks, and result limits. The official name for this collector is a provider.

Request formal approval

Send the proposal to its governing owner. If an approved file changes, rerun the required checks and request a new approval.
