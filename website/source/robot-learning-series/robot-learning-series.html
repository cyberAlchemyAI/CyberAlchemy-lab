Essay 01 / 5 minute read

Writing better movement code

A warehouse robot brings a package to a packing station. As its arm approaches the target, it overshoots, corrects, then corrects again. Eventually the package settles. The routine works often enough to remain in service, but the last part of the movement wastes time and behaves differently with different loads. An agent is asked to improve it.

The agent could slow the final approach, alter the trajectory or adjust the controller. Choosing among them requires knowing what the current program does, which physical assumptions it makes and what counts as a successful placement. That information may be scattered across earlier code, experiments and decisions.

CyberAlchemy Lab could bring those pieces together. This series follows a hypothetical investigation into the robot's movement routine, with research references supplying precedents for particular mechanisms. It proposes an application of the Lab around one question: how could an agent use an explicit development history to make its next decision better informed?

Before changing the code, the agent needs to understand the task. A package must arrive at the assigned position and orientation, within a stated tolerance, and remain there long enough for placement to be confirmed. A motion that passes through the target and immediately moves away has a different outcome. Completion time matters once the placement conditions have been met.

A definition gives successful placement a precise meaning. A contract specifies the information needed to describe an assignment and report its outcome. An experiment records whether a particular routine satisfied those conditions. The agent can compare two programs against the same task.

If the candidate reports success as soon as it crosses the target, it may appear faster simply because it stops measuring too early. The task definition lets the agent detect that error, provided the evaluator implements the rule correctly. Changing an admitted definition would change the obligations of dependent routines and evaluators. Such a revision needs an explicit decision about its scope.

An ontology view could connect the placement requirement to its motion routine, implementation and experiments performed with a particular robot model. These connections help the agent find relevant evidence. A predictive world model serves a different purpose: it estimates what will happen when the robot acts.

For the oscillating arm, that model might combine rigid-body dynamics with estimates of payload, friction and actuator delay. At a chosen time step, its prediction can be written as x_next = F(x, u, theta, e): the next state depends on the current state x, command u, parameters theta and environmental conditions e. A different payload estimate can change the prediction for the same command.

Physics constrains the possibilities the agent considers. Mass and inertia affect acceleration; actuator limits restrict the available commands; contact changes how forces are transmitted. MuJoCo provides a concrete example of a simulator that represents dynamics, actuation and constraints. Its predictions depend on the model and numerical configuration supplied to it. MuJoCo computation documentation

The agent can use simulation to investigate a slower final approach before proposing a physical trial. It can compare trajectories and examine where the candidate becomes sensitive to payload changes. A learned component might eventually help account for discrepancies that the physics model leaves unresolved. Its training data and supported conditions would also become part of the model's history.

DreamerV3 provides a research precedent for learning an environment model and improving behavior through imagined trajectories. Our proposed application asks how to connect such predictions to the exact movement program, task requirements and development evidence. That integration would need its own evaluation. DreamerV3 paper

With a candidate approach in mind, the agent describes the intended behavior: reduce speed during the final approach and confirm that the package has settled before reporting completion. The description identifies frames, units, required observations and responses to missing observations. It gives the code generator something specific to implement and the evaluator something to examine.

Some obligations can be formalized. A command-limiting routine might be required to satisfy abs(u_i) <= limit_i for every actuator channel in its input domain. A proof would establish that property under its formal assumptions. Successful placement and obstacle clearance require further arguments, as does the correspondence between the mathematical routine, compiled program and robot interface.

The agent then compares the candidate with a fixed baseline under the same declared initial conditions. Variations in package properties and model parameters probe the intended operating range. Placement success remains the primary task condition; settling time, overshoot, command violations and computational cost describe the change more closely. Cases used for tuning are kept distinct from cases reserved for evaluation.

Governance helps the agent decide what the results allow it to do next. Authority identifies governing definitions, contracts and permissions, including permitted experiments. Provenance traces a result to the code and model configuration that produced it. Lifecycle distinguishes proposed, evaluated and adopted implementations within their scope. An assignment to improve the robot must be accompanied by authority for the intended effects.

The investigation can outlast the session that began it. The Machine Agent is ephemeral; its short-term memory belongs to the session. Durable Project State provides long-term continuity through context and ontology views that select the relevant code, evidence and decisions. A successor can recover what was attempted and why a candidate was retained or set aside.

Suppose the slower approach reduces oscillation with the familiar package but loses that advantage when the load changes. The agent now has a narrower question: what explains the sensitivity, and which experiment would distinguish the likely causes? The quality of that experiment will determine how much the next code change teaches it.

Essay 02 / 4 minute read

Choosing better experiments

The first candidate improves the robot's final approach for one package and struggles with a heavier one. An agent could respond by generating another controller. It could also spend its next experiment finding out why the improvement failed to carry over. The second choice may save considerable work, provided the experiment can separate plausible explanations.

The agent is developing both a movement routine and a method for investigating such routines. Over several tasks, it might learn when to inspect an interface, recalibrate a model or change the controller. CyberAlchemy Lab could preserve the evidence needed to assess whether those habits make development more effective.

Consider three explanations for the heavier package's oscillation. The movement plan may rely on a payload estimate appropriate to the lighter package. The controller may respond poorly even with an accurate estimate. Or a conversion at the command interface may change the intended command. All three could produce a similar trace at the target. Naming a failure mode helps organize the investigation; establishing its cause requires evidence.

The experiment's recorded connections lead back to the model assumptions, command contract and source revision. Provenance identifies what ran; lifecycle helps establish whether earlier findings concern the current configuration. A unit-conversion defect in a retired interface may suggest a check, but the current interface needs examination on its own terms.

For the payload hypothesis, the agent could inspect the estimate used to plan the movement and compare runs with corrected estimates. Varying the simulated load would characterize sensitivity within the model; physical calibration would need observations of the actual load. For the interface hypothesis, it could compare requested commands with values received after conversion. The investigations reveal different things and have different costs.

An experiment should reduce a particular uncertainty. Hundreds of controller variants may improve a score while leaving its cause obscure. Comparing competing explanations gives the agent a stronger basis for a change. Where factors interact, the design must account for those interactions; changing one variable at a time is only one option.

Formal reasoning can sharpen the diagnosis. An independent requirement might specify the command range and input domain. Lean's proof-validation guidance emphasizes both proof validity and the meaning of the statement proved. The agent needs to examine assumptions and open obligations, especially when code and proofs are generated within the same development process. Lean proof-validation reference

Imagine that the routine limits each command correctly, yet the package still oscillates. A proof of that routine would settle a narrow question about command magnitude while leaving stability and settling behavior open. The agent can use the result to refine the investigation, preserving the proof's actual scope.

Code generation fits within this experimental structure. The agent might propose two terminal timing rules and compare their outcomes. In reinforcement learning, it could generate a reward program used to train a controller. Eureka demonstrates an LLM generating reward code and revising it through evaluation feedback. Assessing direct movement-code generation would require a separate investigation. Eureka project

A training reward and task success also need distinct meanings. Rewarding proximity to the target may overlook whether the package stays there. The placement definition remains the reference for evaluation. A proposed change to that definition or the evaluator needs its own justification and adoption through the appropriate authority.

Suppose the investigation finds a frame-conversion error that earlier tuning had obscured. An operational lesson could recommend checking requested and received commands before retuning this interface. Its record would identify supporting evidence, affected configurations and conditions for reuse. It would also specify contrary evidence, such as comparable investigations where the check adds cost without improving diagnosis.

Classification makes the lesson easier to find. The symptom might be filed under terminal oscillation, the confirmed failure mode under frame conversion, and the lesson under interface diagnosis. Those categories provide different routes to the same evidence. A future agent searching for an oscillating placement can find the case without assuming that every oscillation has the same cause.

To assess that lesson beyond one case, the agent could compare the diagnostic sequence with the previous workflow on other tasks under similar budgets. Measures include time to diagnosis, experiments consumed and regressions missed. Tasks withheld from the process's development would help reveal whether the method transfers beyond the cases that suggested it.

A reflection written after a session supplies a hypothesis about the method's value. Comparative evidence would support adopting it: better diagnoses or candidates, with an acceptable use of time and computation.

Saving an evaluated lesson changes what a later session can retrieve and use; it does not by itself update a language model's weights. Durable learning may also appear in revised code, calibrated physics parameters or a trained controller. The session's temporary reasoning expires. Project State supplies the persistent record, selected through context and ontology views for the next task.

Two connected feedback loops emerge. One changes movement in response to measured behavior. The other changes how the agent diagnoses problems and chooses experiments. The second loop may prevent repeated mistakes or introduce procedures whose costs outweigh their benefits. The record must allow either result to be recognized.

A candidate that eventually meets its formal and simulation criteria gives the agent a reason to prepare a physical trial. The development history explains its selection and identifies uncertain assumptions. Those assumptions indicate which observations may be most informative when the routine meets the robot.

Essay 03 / 4 minute read

Learning on the robot

The investigation returns to the packing station. In simulation, the candidate routine settles more smoothly across the selected package conditions. Some code properties have also been proved under explicit assumptions. The agent now needs to compare its predictions with measurements from an authorized trial on the warehouse arm.

The simulator predicts how the arm should respond; the robot supplies measurements from a physical trial. Differences can teach the agent about the code, the model or their connection, provided the investigation preserves enough information to distinguish the explanations.

The candidate's implementation package identifies the source revision, executable build, configuration, interface contract and supporting evidence. Authorization specifies the robot, task and conditions for the trial. The agent needs to establish both its technical ability to send a command and its permission to produce the intended physical effect.

Movement depends on a chain of interpretations. A request becomes a target in a declared coordinate frame. The program produces a reference trajectory; the controller converts tracking error into actuator commands; the interface delivers them at the required rate. Sensors supply placement observations. Incorrect units, timing or calibration at any connection can change the behavior.

The agent needs evidence that the evaluated code corresponds to the program used in the trial and that its interface bindings are correct. A trajectory must reach the controller in the expected frame. Assumed delay must be compared with observed timing. The Lab could make these correspondences explicit enough to inspect after an unexpected result.

The deliberating agent and motion controller work at different timescales. The controller executes the adopted implementation at the required rate. Between experiments, the agent examines results and prepares changes, while the robot can continue using its known implementation. An adaptive controller could update within a declared operating envelope; extending that envelope requires a further decision.

The physical package may have a different mass distribution, the grip may introduce contact effects, or execution delays may vary. Evaluating across simulation parameters can help investigate these differences. The range needs physical justification: its usefulness depends on covering conditions relevant to the robot.

DrEureka provides a research example of language models helping construct reward functions and simulation parameter distributions for transfer to physical robots. Applying a similar method to our arm would require evidence for this hardware and task, including the simulator's adequacy and the chosen parameter ranges. DrEureka project

Suppose the trial produces more oscillation than predicted. The record includes position traces, commands, timing and placement outcomes, tied to the exact implementation. Before diagnosing the discrepancy, the agent assesses measurement quality. Missing observations or uncertain clock alignment may prevent a useful comparison with the prediction.

If a command arrives later than assumed, the agent can examine how delay affects predicted movement. If timing agrees, payload calibration or contact behavior may deserve attention. Further observations, parameter changes or code revisions follow the evidence, with alternative explanations retained until the investigation can distinguish them.

A revised world model changes the basis for code evaluation. Earlier evidence remains in the history, but its applicability needs reconsideration. The ontology helps the agent find experiments and candidates that depended on the changed assumption, then choose which comparisons to repeat.

Physical effects can also become uncertain. A command may execute before a connection fails, leaving placement unconfirmed. Repeating it could act on a package that has already moved. The agent first uses an applicable observation procedure to reconcile physical state. The issued-command record supports recovery, but cannot establish the package's location by itself.

Governance answers practical questions here. Authority identifies what governs placement and who may change or execute the routine within scope. Provenance traces observations to their implementations. Lifecycle identifies proposals, evaluated candidates and adopted or superseded records. The agent uses these distinctions to determine which evidence applies and which next actions are permitted.

A routine may be adopted for one package class while another remains under investigation. Evidence can support extending that scope, reveal a regression or justify withdrawing a candidate. The agent prepares the proposed change; the decision follows the required authority, including limits on its delegation.

A later session reconstructs this position from Project State. Context and ontology views select the applicable implementation, unresolved discrepancies and lessons. The Machine Agent remains ephemeral, with short-term memory attached to its session. Continuity depends on records that another session can examine and use.

Physical experience can improve the experimental method too. If execution delay repeatedly explains problems missed in simulation, the agent could propose using measured delay variation in future evaluations. It would assess whether this detects problems earlier and improves the candidates reaching physical trials.

Maintaining this history also consumes time, computation and storage. An empirical evaluation should examine completion, constraint violations, recovery and regressions alongside those costs. The architecture earns its place if the preserved information helps agents make better decisions under comparable conditions.

The next unfamiliar package gives that proposition a concrete test. A new session could locate the routine's adopted conditions, inspect its payload assumptions and retrieve an experiment that previously distinguished causes of oscillation. Further code changes and measurements may be needed. The useful continuity is an examined history from which to begin, and a clearer account to leave of what the robot can do.
