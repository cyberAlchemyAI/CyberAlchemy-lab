An agent’s working session

A new AI agent starts the export investigation on Monday. It has no private recollection of last week’s review. It needs the selected software, current evidence, project goal and permission to use tools. CyberAlchemy Lab organizes those inputs into an explicit session—a temporary working period for one machine-agent instance—while saving useful project knowledge outside the agent.

Actor is the general classification for an identifiable participant. A Person is a human; a Team is a continuing group; a Principal is an identity recognized for authentication, authorization, ownership or accountability at a particular boundary. A Role describes a position; Responsibility describes what a participant must answer for. Team Membership and Role Assignment record belonging and role occupancy separately. References point to these identities without making a person, account and role the same thing.

Agent classifies an operational actor. An Agent Profile records reusable behavior, inputs, outputs, tools, evidence, escalation and stopping conditions. An Agent Capability describes a class of attempts the agent can technically make, including input, output and failure requirements. An Agent Instance is one concrete realization, with its profile, implementation, capabilities and accountability identified. Concrete participant kinds have their own records; the model does not require a duplicate universal Actor record for each one.

An Agent Assignment identifies expected participation in particular work, intent, project, goal, run, role or responsibility, with limits and deliverables. Delegation separately records permission from an authorized owner or principal. For the export, the job might be to diagnose missing rows while permission covers only reading selected sources and proposing a fix. Customer communication and production changes remain excluded. Knowing what to do and being allowed to do it are different facts.

Saltzer and Schroeder’s least-privilege principle confines a program or user to the permissions needed for its work. Complete mediation calls for checking authorization whenever access occurs, including relevant changes to earlier permissions. These principles explain why an old instruction cannot indefinitely authorize actions. They provide design guidance; they do not demonstrate enforcement on every Lab execution path. [Basic Principles of Information Protection](https://web.mit.edu/Saltzer/www/publications/protection/Basic.html).

An Agent Session identifies one instance and assignment, its Context and Ontology Views, policies, permissions, inputs, resource limits and termination conditions. A machine instance belongs to one session and ends with it. Profiles and historical session records can persist in project records. The operating machine worker and its working memory are temporary; they do not continue privately across sessions.

Project State supplies saved knowledge: records, definitions, decisions, evidence, histories and connections. Every included record retains its own standing; inclusion in an accepted state does not by itself accept a proposal or promote a source. A Context Request asks for what this session needs. A Context View supplies a fixed selection, identifying sources, versions and use conditions. An Ontology View supplies a selected connected model from a consistent recorded state, called a cut. Together they provide task information and relevant relationships while retaining the authority limits of their sources.

Session Memory holds temporary notes, intermediate alternatives and reminders for one session. It ends when that session terminates. A useful note can be proposed as a saved reflection, evidence record or lesson through the applicable record and approval process. Retaining a private note is not the same as adding it to Project State. A future agent reconstructs its position from saved records and newly prepared views.

The inspected local runtime implements a limited version of this contract. Notes stay in process memory, have an entry limit and are cleared on closure. The session identifies the selected accepted-state reference, source selection and expiry time. A changed state reference, changed source digest—the file’s content fingerprint—or expired interval invalidates the context for continued use. The response is to prepare and check current context through the applicable process.

An exported context packet is a saved result of preparation, not a continuing session credential. The runtime’s context-only export closes the session after preparing that packet. A later consumer must establish the information freshness and permissions needed for its own session. Keeping the file does not keep the earlier machine instance alive or preserve its expired permissions.

An Agent Action records who proposed, attempted, completed, rejected or failed an operation, with its session and relevant inputs. A Tool provides a versioned interface for invoking an operation. Tool availability, technical capability, the recorded action and an observed effect are separate facts. A Work Outcome Assessment compares an expected result with the result observed; it does not automatically prove wider benefit.

The agent can now prepare current information, inspect its job and permissions, choose permitted tools, record actions and produce results with evidence and unresolved work. Proposed changes to saved project records follow their required review and authorization process. After closure, another agent can inspect the accepted results through new views without inheriting private memory or unrestricted permissions from its predecessor.
