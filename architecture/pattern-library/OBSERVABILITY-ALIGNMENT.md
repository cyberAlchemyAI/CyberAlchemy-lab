# Observability alignment

Audit-derived map, authority effect none.

| Concern | Available observation | What it does not establish |
| --- | --- | --- |
| Construction progress | Plan0011 execution-state task statuses, exact accepted_evidence and claim_ceiling fields | Product percentage, admitted state or successful final operation |
| Source currentness | Source/profile/schema manifests, exact guards, captured epochs and input accounting | Runtime qualification from metadata review alone |
| Agent/session | Actual context expiry, phase timings, trusted exception/terminal observations and cleanup records | Uninstrumented production latency or calibrated reserve from deep instrumented counts |
| Native effect/retry | Operation journal, independent receipts, lock/custody/replay evidence | Real owner outcome from fixture-only controls |
| Work and learning | Workflow outputs, lesson selection/application/assessment identities | Benefit from persistence, display or selection alone |
| Ontology | Selected mapping/projection and governed exact-semantic-event join | Universal source/domain coverage or semantic authority |
| Documentation | Exact source edition, selected source map, static build/search/preservation manifests | Current executable admission/qualification or live service health |

## Proposed status composition

A current status view should bind independently:

1. repository Project State/Decision selection;
2. executable/API/source/profile and exact capture;
3. task construction state;
4. actual operation/terminal/recovery outcome;
5. governing scope/outcome and applied effect;
6. product/human benefit and release state.

Preserve historical failure observations while adding successors. Do not overwrite an expired episode with a later PASS or use an updated prose date to refresh stale evidence. The family4-to-family5 correction in the audit illustrates why these axes must be visible together.
