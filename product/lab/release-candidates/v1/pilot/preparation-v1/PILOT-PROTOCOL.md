# R05 candidate pilot protocol

Status: prepared protocol; no participant enrolled and no pilot executed.
Authority effect: none. This document records prospective measures, not results.

## Entry conditions

The pilot episode may start after exact R02, R03, R04 and O07 evidence meets the
scope required by R05. Its episode manifest must bind this protocol, the selected
Product thesis and capability, source cut, qualified API source and profile,
qualified context implementation, permitted operations, current local policy,
owned temporary workspace, and the real participant's agreed task. An expired
grant, incomplete API qualification, or failed Machine transport blocks the
affected journey. Development-suite output cannot close this pilot.

The participant chooses genuine repository work. Before the first attempt,
record their question, success condition and selected subject; freeze those
choices in the episode manifest. A participant identifier records study
participation; it conveys no Principal identity or governing role. Bind actual
runtime authentication separately. Obtain a real participant response for
enrollment and usefulness assessments; an Agent cannot supply those responses.

Use the existing candidate-development authorization only for owned isolated
local candidate effects. No live store, persistent credential, network service,
canonical admission, installation, activation or external publication belongs
to this protocol. Admission and adoption outcomes stay pending R08/A01–A03.

## Journeys and measures declared before use

| Journey | Participant task | Required observations |
| --- | --- | --- |
| Engineering | Answer one real question about a selected definition or capability's current state; trace its contract, exact source and unresolved gaps. Prepare an isolated candidate change only if that action is separately within the selected grant. | Correctly located identity, revision and authority state; time to answer; participant corrections; missing or misleading evidence; actual operations and costs. |
| Research | Inspect one real research/evidence question and distinguish the supported finding from a hypothesis, counterevidence or missing evidence. | Exact source references; unresolved claims; participant's explanation of the evidence ceiling; time and effort; any unsupported inference caught during review. |
| Fresh Session | Open a qualified, authorized ephemeral Machine Session from current Project State and bounded Context/Ontology views; perform the selected read; close it; start a distinct new authorized Session. | Exact cuts and inputs; actual Agent/Session identities; limits and expiry; real disposal evidence; durable-state lineage for the second Session; no transfer or restoration of first-Session RAM or signer. |

If the selected API lacks a required operation, record the journey as unavailable
and leave its obligation open. Each Journey must represent actual work and use;
fixtures and demonstrations remain engineering evidence with their own scope.

For each attempted journey record:

1. Real wall-clock start/end and observed elapsed time, including setup,
   authentication, waiting and recovery. Separate participant active effort from
   unattended compute when it can be observed; otherwise state it is unknown.
2. The participant's original question, declared completion criterion and actual
   answer. Bind any recorded response to the source conversation or retained
   observation; do not infer satisfaction from a successful API reply.
3. Exact public request/reply bindings, operation receipt, contract/source cut,
   selected grant and implementation evidence. Store sanitized public evidence;
   keep keys, bearer proofs and RAM outside the pilot package.
4. Success, failure, unavailable or unresolved result against the declared
   criterion. Preserve negative findings, timeouts, expiry, refusal and recovery
   costs. A negative case needs its actual cause; an unrelated expiry does not
   prove the intended authorization refusal.
5. Participant-reported usefulness on a declared five-point scale: 1 unusable,
   2 substantial extra work, 3 mixed/unclear, 4 useful with some correction,
   5 useful without substantial correction. Record missing response as unknown.
6. The participant's explanation of what was useful or burdensome, their desired
   simpler alternative, and any suggested operational lesson. Proposed lessons
   need evidence and their own workflow; observations do not automatically admit
   or apply lessons.

## Baseline and interpretation

Before candidate use, ask the participant to answer the selected engineering
and research questions using the repository's existing file/index workflow.
Record actual elapsed time, answer correctness and effort with the same measures.
Use the same frozen subject and source scope for candidate use. If the baseline
cannot be taken, retain candidate observations but make no improvement claim.
Baseline-first order may teach the participant the answer; record that limitation
and do not treat the observed difference as a causal Product-value estimate.

A result supports only the observed participant, tasks, source cut, candidate
implementation and permissions. Counts, correctness and observed costs may be
reported directly. Product benefit, full capability realization and general
Agent safety remain claims requiring additional evidence.

## Review and completion

Prepare an evidence table containing every attempt and its declared measures,
including negatives and missing data. Reconcile the table against actual
operation logs and participant responses. Identify mismatches and unresolved
evidence before writing a pilot receipt. The receipt must bind actual observed
outputs and explicitly distinguish candidate use from admitted operation.

R05 is closed only by genuine user/work/evidence and cost observations covering
its declared journeys, actual adoption/permission scope, negative findings and
claim ceiling. This prepared protocol closes no R05 criterion. Admitted-operation
obligations remain A03 after the actual R08 decision.
