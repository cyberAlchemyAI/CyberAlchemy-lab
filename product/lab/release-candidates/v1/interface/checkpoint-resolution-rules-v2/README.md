# Exact checkpoint resolution rules

This candidate supplies the pure verification portion of `checkpoint.resolve`.
It retains the original public schemas and original native core/content functions.
Every required voice appears in core and voice order. The package, checkpoint,
bundle, complete targets, stable cores, validation, examples, privacy evidence and
original source proofs remain bound to their exact bytes. The all-required flag is
computed from every verified response. Reject and defer are recorded outcomes;
neither authorizes an all-or-nothing bundle. Construction gaps remain visible even
when every signed response selects approval.

Signatures cover the exact package, checkpoint, cut, core, Principal, Role, outcome,
channel, recognition, provenance, bounded period and nonce. A request supplies no
signer key or recognition. The host supplies independent typed channel and owner
facts. Their original descriptors and provenance must match every supplied field.
Unknown, duplicate, reordered, missing, changed, expired or revoked inputs fail.

The three public channel shapes are explicit: operator signature, owner
conversation and existing exact authority. Conversation and existing-authority
signatures represent the selected verifier's attestation; their human identity,
actual message interpretation and current authority require their host adapters.
They are not inferred from text, Role declarations or possession of a key.

The kernel validates cryptographic and byte consistency against supplied facts.
It does not independently establish that those facts represent current recognized
owners. Public authentication, live Role/Assignment/Scope resolution, current
provenance adapters, before/after host guards, durable recording, retry/recovery
and original Validation Report production remain required for API integration.
`checkpoint.resolve` remains unimplemented in the current API host.

The rule fixtures are synthetic. They use fresh keys held only in test memory,
two members and three required voices, original native core/content computation,
noncanonical target bytes and signed approve/reject/defer responses. Forty-seven
cases cover exact coupling, all three channel shapes, computed approval, retained
gaps, signature forgery and replay, expiry/revocation, spoofing and unchanged
inputs. These fixtures provide no actual owner outcome, canonical admission,
Agent memory, live store, service activation or completed-plan evidence.

The original v1 run stopped in registry setup because the original storage schema
and its exact native copy have the same identifier. Both are retained and guarded.
Version2 registers a byte-identical copy once and rejects any different original
bytes under the same identifier. All45 original test methods are unchanged; two
additional cases verify exact-copy handling and refusal of a whitespace-different
schema with the same identifier. The v1 failed report remains unchanged.
