# Exact release readiness and evidence custody

This successor can prepare a `ready` proposal-review once independently selected actual evidence closes the exact candidate. Returning `ready` prepares final review; it does not approve release, publish, install, activate services, admit canonical artifacts, create a human response or create the final R08 Decision.

The private installation/release custody plan selects a closed `lab-release-readiness-contract/v2-candidate` binding independently of the public ReleaseManifest. The contract binds the exact manifest/cut, actual predeclared `release-scope.json`, all thirteen AC01–AC13 obligations, six evidence classes, reviewer public keys/private custody grants, and any explicitly required prior owner prerequisites. Governing RoleAssignments are verified only when such an owner prerequisite is independently selected; evidence collection does not invent a governing role or force admission of representations awaiting the final R08 checkpoint.

Each evidence requirement selects exact `lab-release-readiness-evidence/v1-candidate` bytes and an Ed25519 attestation. A separate evidence-custody grant is signed by the actual authenticated private reader-policy issuer key. It binds the recipient identity/public key, evidence classes, exact candidate/source scope, trusted original human-source bindings and a real validity interval. Its effect is only candidate evidence authenticity; `governing_role_granted` and `owner_approval_granted` must both be false. The evidence signature binds this exact private grant along with the evidence, candidate, cut and named obligations. Both signatures, original bytes, private policy and real clocks are checked afresh. Cryptography alone does not establish the factual truth of an observation.

Actual closure requirements:

- API qualification: exact current API source/profile; all original34operations implemented; all323original cases retained; complete PASS aggregate with every case passing; actual successful terminal records; actual schema-valid public calls covering all34operations. Full frozen source verification remains required.
- Human pilot: exact predeclared R05 protocol and episode/permission records; genuine engineering, research and fresh-Session attempts; real questions, criteria, start/end/duration, answers, operation bindings and negative findings. Enrollment, usefulness and every participant answer must match exact retained original `user` entries at the selected conversation/participant, under the independently authenticated trusted source selection. Agent text, ambiguous entries, missing provenance or unselected sources cannot become human evidence. Missing baseline prohibits an improvement claim.
- Acceptance: independently reviewed actual measurements for every named AC condition, preserving candidate operation scope.
- Privacy: exact privacy-review binding, complete implementation/package material coverage and absence of private credential/Session memory export. Candidate preparation grants no publication permission.
- Installation: actual original-schema installation/rollback receipts, exact selected environment, complete verified postimage/evidence bindings and zero service activation.
- Review closure: exact complete candidate member list and transitive byte closure; declared digest edges must equal original bindings actually found in the bytes, and the actual graph must be acyclic. No selected gaps may remain. Explicit prior owner prerequisites must have actual current positive evidence; final R08 remains separately required after preparation.

Readiness is dynamic: absent or invalid actual inputs produce blocking gaps; complete valid actual inputs can produce `ready-for-final-review`. Current fixtures have no complete API/human-pilot/owner outcome and create no positive whole-Lab readiness example.

The implementation uses the already qualified `guarded_candidate.selection` only around pure preflight reads. Full original signed-source checks occur at scope entry/exit, and no durable installation/evidence publication occurs inside that scope. Actual Vault.guard already performs ReaderChannel.guard. Publication, active-descriptor commit, recording and exit retain actual source/permission callbacks outside the pure scope.
