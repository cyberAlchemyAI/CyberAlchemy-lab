# Lesson Application: current Session composition

## Defect in the predecessor

API82's application policy belonged to the metadata preparation family. Its
authentication guard required `session_control` to be null. Its application
preparation required the same host's actual `ContextSessions` and `LiveReader`.
Those conditions cannot hold together. Preparing all prospective bytes before
authentication also requires knowing the future Session identifier.

## Candidate successor

API83 declares a separate, closed private application policy with the original
current participation grant, exact source period and Session control. It admits
the original twelve host operations plus application preparation. The Machine
peer's original seven read operations remain the whole peer allowlist.

The private policy binds one pair of future Session and Agent identifiers. The
operator can use these identifiers in prospective application bytes before
authentication. An identifier declaration creates no resource or memory. The
original source/Assignment/Profile/Implementation/Capability eligibility and
delivered Context checks must pass before opening allocates the live resource.

The host then reserves both identifiers in its owned private journal, outside
the pure fact scope and before constructing RAM state. Reservations contain
identifiers and the exact opening request binding only. Partial reservation or
opening failure requires inspection; a different key cannot reuse identifiers.
Existing Session events also refuse reuse after actual disposal. Exact retries
use the original operation journal and cannot reconstruct a lost resource.

The original real clock, source period, strict deadlines and 900-second ceiling
remain. Closing clears RAM and disposes credentials. Durable continuity remains
Project State from Context and Ontology views. The application method checks
that the actual live Session is the private policy's selected identifier.

## Workflow and authority

1. Prepare exact prospective content, core metadata, selection, applicability,
   instruction and optional scoped override evidence for the declared identity.
2. Bind the routing object, application method and identifiers in the private
   policy, together with current participation and development authorization.
3. Authenticate the actual operator, obtain same-cut Context, and open the
   actual Session through the original eligibility calculation.
4. Prepare the attributed application ChangeProposal with that live Session.
5. Validate and review the complete candidate package at the final checkpoint.
6. Admission or tool execution requires its own actual authority boundary.

No new intermediate owner approval is introduced by this candidate repair.
The existing construction authorization covers the successor and isolated
checks; it does not supply canonical admission or tool action permission.

## Qualification ceiling

The signed current source still has no current Lesson Application records.
Policy/identity composition checks and an actual opening/closing example do not
qualify positive lesson application, outcomes or the whole API. Those require
the real controlled lesson episode, original affected suites and full plan
integration. This successor still has 23 authored handlers and 11 missing.
