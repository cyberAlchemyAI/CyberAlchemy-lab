# Commerce native ABI and realization scopes

This is the EC05 contract for future native producers. `src/commerce/commerce-native-v1.ts` names the exact exports required by the ten selected primitive obligations. The interfaces implement nothing. Core owns this file and its exact Alch mirror. No new native implementation version/hash, public root export, store, handler, worker, provider, runtime availability or loaded basis is claimed here.

## Scope and actual producer barriers

A derived v5 package has an explicit RealizationScope: kind, nonempty source RoleSelector targets and the fixed omitted-capability posture unsupported-not-silently-executed. The original Core recipe independently reconstructs the target's source dependency closure and native requirements. A caller cannot underdeclare a target's capabilities to execute it. Empty targets, stale/foreign source, incompatible role, unsupported call or a family set inconsistent with the actual typed closure reject.

The checked technical model can describe the complete application while a selected package realizes only a verified target closure. Its obligations and actual resolved dependencies must match that scope. Wider requirements stay unsupported/unrealized until their real producers exist. This permits the DAG's pricing-first and local-effects-first joins; it does not make the final application optional or fulfill any full-application output from a smaller scope. A normal full application generation request selects application scope and refuses missing native implementations. Code/API/views identify their exact selected source/realization scope. No silent fallback or profile relabeling is allowed.

ServiceModules can emit static module structure as a pure generator component before whole-application composition exists. Pure component output is not an application handle. Actual composition of service owners/ports is the later ServiceComposition native primitive. Root/profile/source selection precedes early requests and review; original accepted decision/input/checked role graph precede generation; actual emitted/imported bytes precede late binding and full system/bridge projection.

## Value and expression boundary

UInt64 is bigint internally and canonical unsigned decimal JSON text on wire. Native optional values use none/some tags; JSON null is their wire representation only. Records/enums/lists are closed, checked and copied; the exact source schema controls refinement, invariant and size checks. Private context projections are not serializable ValueType and have no decoder constructor. Value schema parsing selects an explicit data root and its reachable type closure; the per-expression64record limit is not a global limit on every DTO in an application. Schema and computation checking may issue component-owned handles from valid data; that does not issue an original application, decision, actor or native basis.

The bounded value module has four functions: checkCommerceSchema, decodeCommerceValue, encodeCommerceValue and copyCommerceValue. The computation module has checkCommerceComputation, compileCommerceComputation and evaluateCommerceComputation. Pure schemas, ASTs, budgets and source roles must pass their assigned independent checks. A Rule false is a successful Boolean; arithmetic/type/budget failure is a separate typed outcome. Neither input nor profile can inject a predicate, comparator, evaluator or dependency override.

The eleven identity producer signatures must match the actual EC03 context contract and source call sites exactly, including confirmedOrderFingerprint's customer/lines/amount/currency/reservation/payment fields and exclusion of occurrence metadata. Factories are bound to an original live generated-operation invocation and selected source callsite. Creating a proxy does not evaluate a clock or allocate an ID; source order still returns accepted replay before new clock/Order-ID/effect calls. Actual registered producer methods validate their domains/currentness. A caller cannot replace the clock/hash or obtain original private custody by copying fields.

## SQLite representation and transaction settlement

The selected physical driver is Node's pinned node:sqlite.DatabaseSync. Each service opens only its registered scratch store descriptor/path. The descriptor comes from the original checked graph and actual generated migration/query bytes at assembly; a schema-shaped JSON object or supplied SQL string cannot open or change a store. Fresh schema creation/migration is an explicit generated setup action, never an implicit change of an arbitrary existing database on service open. Wrong owner/service/path/schema epoch denies. No live database is selected.

Full-range UInt64 fields, including versions, remain canonical decimal TEXT and checked bigint values at the native boundary. They never use SQLite signed INTEGER or JavaScript Number for business arithmetic. A closed row payload may be stored as canonical UTF-8 wire bytes in BLOB; indexed identity/unique keys use the exact typed length-prefixed byte tuple. Text/SKU key bytes preserve Unicode scalars and embedded NUL/control values admitted by the source; no SQLite string function may trim, normalize or reinterpret them. SQL identifiers come only from validated prefix and checked service/node names; values are bound parameters.

Selected queries use declared identity/unique-key lookup or bounded key sets, followed by the checked predicate/projection. Stock batches have at most100 unique source SKUs and stable binary UTF-8 order. Version compare-and-set compares canonical decimal text exactly; arithmetic happens in checked bigint code. Any supported numeric ordering/range must use a proved exact decimal-length/binary-digit relation or the bounded checked pure comparator. Unsupported unbounded scans, numeric coercion or new SQL operations reject before emission/binding. A row count is converted only after a known safe integer/bigint range check.

applyCommerceTransaction receives an original source transaction handle, service store, private live generated invocation and bounded bindings. It validates all reads/guards/participants/expected versions and forms all results/events before changing rows. Mutations, declared receipt and outbox commit locally together; no cross-service transaction is implied. Constraint/version failure returns only after proven local rollback. A thrown exception, timeout, absent row or lost reply does not establish rollback. Uncertain settlement returns an indeterminate ticket retaining actual resources/identity; close reports retained-active-resources until real settlement/quiescence. No JSON outcome or stored Boolean can be supplied back as an original receipt/ticket.

Command inspection uses the original command/receipt locator. Recorded, pending, missing, conflict and unknown remain distinct. A missing row after uncertainty is not a no-effect witness. Only original proven local rollback can take its explicitly declared same-command retry path. Accepted/unknown records are not evicted to admit new work. The source's4096capacity rejects new intents. Prepared/dispatch and transaction claims retain original request content; a new key is never an uncertainty workaround.

## Entry, Auth and raw transport

The HTTP module binds actual imported output to the original checked entry and bounded configuration. createCommerceRequestHandler exposes Request/Response only; it does not accept a business invoke callback. The handler remains injected, with no listener/TLS. Original actor and causal owners come from registered private infrastructure; request body/headers cannot construct authority. Each logical entry retains its own permission and source/resource guard phases. Current action access precedes replay; fresh-intent and scoped-query guards run at their declared phases.

Auth uses the actual fixed READY/admission/decision chain in the EC04 contract. A fresh original context seals entry, input bytes, actor/caller/resource/causal/source/profile/native epoch. Consuming it creates one live generated-operation invocation; it is not a worker lifetime capability. Store/identity/helper calls require the matching live invocation and current source descriptor. An unknown local effect retains resources instead of becoming a safe cancellation. No hostile in-process host isolation, JWT verification, live user assignment or distributed atomic revocation guarantee is claimed.

Raw I/O is a separately registered private infrastructure port handle. It supplies bytes/transport observations, never a per-feature capture/retry/query/price/permission function. Factories and late binding must recognize original selected port/source/native owner records. Component raw-wire validators can return checked data; their success does not prove physical delivery or business completion.

## DemoPay, events and workers

The DemoPay module has createDemoPayV1Client and validateDemoPayV1Observation; the original client exposes Capture and InspectCapture. Types match the actual four-field request and six-field result. Wire status/headers/schema/bytes are checked. Captured/DefinitivelyDeclined require a reference, unresolved/unknown-key require none. Well-typed mismatched identity/amount remains observed data for the mandatory source conflict Rule; malformed wire is a typed failure, never a fabricated decline. Same key/content may resolve from pending/unknown but cannot create another capture or flip a definitive result. Inspection is read-only. The selected synthetic raw peer, persistence/fault windows and original-call lineage are qualified only at EC26/27; no commercial money movement is inferred.

The event module encodes source-selected event data, creates an explicitly pumped outbox relay, and consumes original producer occurrences. Creating a relay does not start an unbounded background pump. relayOnce and close are owner methods. Transport acceptance and consumer completion are separate observations; absent peer evidence stays not-observed/unknown. An outbox row originates from actual local commit. Inbox identity, complete event fingerprint, source consumer result and acknowledgement match the declared transaction. Actual consumer local commit is required to observe completion; no payload receipt can manufacture it.

Worker creation does not grant a claim or start dispatch. claimCommerceWork recognizes the actual generated claim transaction and returns original lifecycle ownership, contention, uncertainty or unavailability. resumeCommerceWork follows the checked source workflow and actual current snapshot/claim. Journal Prepared/Dispatched/Observed data is not itself custody. Private quiescence and original never-dispatched evidence are required; timeout/lease/JSONworker fields are insufficient. Replayed observations cannot renew fresh continuation tickets. Terminal finish may change declared technical schedule bookkeeping but cannot secretly change Order state. The original command/attempt is retained on every unknown branch.

composeCommerceServices and bindCommercePorts consume original imported service and registered port/native owners at the requested scope. They accept no raw application evaluator or arbitrary JS/SQL template. Missing/foreign/stale/generated-output mismatch fails before publication/execution. Context/worker/store/port/native handles cannot be serialized or restored from inspection metadata.
