# Xero exact draft-bill posting and inspection

`createXeroConnector({account,supplierId,accountCode,taxType,currency,credentials,http,assertCurrent,apiRevision})` reuses existing neutral API/effect owners for one selected supplier/account/tax/currency. The neutral `draft-bill-create-inspect/v1` operation `bill.draft` takes invoiceNumber/correlationId/date, bounded exact lines/total, original idempotency key/time and approval/manifest digests. Only ACCPAY DRAFT is emitted. Authorisation, payments, credit notes, attachments and arbitrary invoice fields are unsupported.

Setup reads `/connections`, the exact supplier, accounts and tax rates to verify the configured tenant, active supplier, account and tax type. Required scopes are `accounting.transactions`, `accounting.contacts.read`, `accounting.settings.read`. The selected currency subset uses two minor decimal places; NONE tax requires zero tax. A separate authored approved tax policy supplies other exact tax amounts. This is not a general tax engine.

PUT `/api.xro/2.0/Invoices` emits exact decimal-number JSON directly from UInt64 minor-unit strings, including values above JavaScript's safe-integer range. No business amount crosses JS Number. Provider numeric lexemes are decoded losslessly and matched as exact minor units. An actual provider that rounds or changes selected values fails reconciliation. Source/fixture correctness does not qualify that hosted numeric behavior.

The header key must be SHA256 of the original R02 logical intent ID. [Xero's idempotency guide](https://developer.xero.com/documentation/guides/idempotent-requests/idempotency/) limits retained keys to six minutes; after that window new posting rejects. Unknown/expired work only inspects the original ACCPAY Reference, InvoiceNumber and supplier. The bounded first page accepts exactly one matching invoice, then GET by InvoiceID verifies DRAFT/current fields and exact totals/lines. Absence or multiple candidates remain review; no universal duplicate-proof claim or new-key blind repost. Wire fields follow the [official AccountingOpenAPI schema](https://github.com/XeroAPI/Xero-OpenAPI/blob/master/xero_accounting.yaml).

## Runtime boundary and lifecycle

The factory consumes a trusted `http(request)` seam; there is no default network client or SDK. Request fields are exact HTTPS URL/method/headers/owned bytes, the existing signal/total deadline, 262144 response-byte bound, `redirect: error` and `maxRetries: 0`. Each native operation makes at most eight selected requests, each bounded by the same total deadline and a 15-second local maximum. The HTTP implementation must enforce these limits during I/O; the adapter independently checks returned byte/status/shape bounds. Test transports return explicitly synthetic recorded HTTP responses and never contact a provider.

`credentials.current({provider,account,operation})` returns trusted current `{token,account,scopes,revision,status,expiresAt}`. The credential owner verifies account/scopes and refreshes or rotates secrets outside business payloads; this adapter checks its current exact-account binding before every request. Revoked, expired, unavailable or mismatched credentials stop new dispatch; there is no automatic refresh/replay or second account/provider. `assertCurrent({provider,account,operation,command,binding,inspection})` must synchronously enforce the actual current Entry/approval/source/resource authority; serialized command digests do not grant authority. Recheck occurs before/after awaited HTTP.

`encodeCommand` admits only the named finite neutral contract/version/operation and selected fields. `createSlot({id,operation,resourceId,action})` returns the original R02-compatible `execute/inspect/validateObservation` slot with source release required. Install it in the existing effect dispatcher: R02 owns logical intent/payload conflict, durable attempt identity, bounded retry/backoff/rate/concurrency/circuit policy, one-use dispatch custody, source-release tickets and unresolved retirement. This connector owns no attempt database or alternative retry loop. Unknown writes are inspected with the original payload/account, never automatically repeated. Definite pre-dispatch denial and documented400/401/403/409/422/429 errors are distinct from uncertain transport/5xx/redirect/partial/malformed outcomes; operation-specific inspection may remain unknown. Retry-After metadata is capped at60seconds and never starts a retry here.

`retire()` stops new connector execution and preserves inspection with current credentials/grants. First use the original dispatcher retirement operation to reconcile unresolved attempts or explicitly retain them for review. Original source/effect owners retain their receipts and protect payload retention/deletion. No local receipt is an account/provider certification. `artifactIdentity()` hashes actual owned module/package/shared-helper bytes; the parent integrator supplies the complete public package/export/dependency closure and generated consumer qualification.

## Open Questions

The implementation is tested in synthetic recorded-wire/local mode. Real account availability, token provisioning, source/recipient policy, hosted API changes and actual provider behavior remain separately qualified operands. DTO/schema/semantic-version drift rejects; a package hash does not freeze a hosted API. Full bidirectional synchronization, unrestricted pagination, provider migration/coexistence/failover and stronger duplicate/delivery guarantees remain outside this selected subset. Local hosting, publishing, deployment, TDE and EVF remain deferred.
