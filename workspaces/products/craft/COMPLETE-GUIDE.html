Step 1 · The business question

Should this account be recommended for renewal?

The Customer Success example has 8 active seats out of 10 licensed seats. Two recorded activities add 5 and 10 points. The authored score is 80 + 5 + 10 = 95. With no open escalation, the authored policy suggests Renew.

A reviewer may approve that recommendation for account version 3. A review of version 2 must be rejected as stale. The request also carries a discussion and source references; the local review cases provide them. The connected cited-answer path has additional provenance checks. These are teaching rules, not a prediction or industry standard. See the actual account fixture.

Step 2 · The product

What Craft does with that decision

Craft keeps business meaning, application construction, and observed behavior connected. The team chooses the account and review rules. Craft checks supported declarations and combines them with selected implementation profiles. A local exercise then runs the generated candidate with named inputs.

1. Describe meaning

Write account types, validity, score, action policy, review behavior, and access requirements.

2. Build a candidate

Select supported storage, HTTP, Auth, and service layout profiles. Craft checks and generates the application.

3. Observe behavior

Run the candidate with fixture inputs. Keep the result and its environment together.

Craft does not choose the renewal policy. This example uses local Auth and SQLite fixtures; production resources and live data need separate work.

Step 3 · The vocabulary

Meta types give each part a job

A meta type says what role a declaration has. A value describes an account snapshot; an Entity identifies a saved account; a Rule answers yes or no; an Operation carries out an action. Craft can check their connections because these roles are explicit.

This application uses nine of the 13 active backend meta types:

Meta typeJobIn Customer Success
Value ObjectA value described by its fieldsAccountSnapshot, ReviewRequest
EnumOne named choice from a setRenew, AdoptionReview, SupportReview
EntityA stored thing with identityStoredAccount, StoredRenewalReview
RuleA yes-or-no conditionAccountNumbersValid
CalculationA typed value computed from inputsHealthScore
PolicyA decision from ordered casesSuggestedAction, RenewalEligibility
MappingA translation into a target valueToRenewalReview
QueryA declared readReadAccount
OperationA declared action and resultReviewRenewal
What about the other four backend meta types?

Interface describes an exposed boundary; Event names something that happened; State Machine describes legal state changes; Workflow coordinates ordered work. They are part of the model, but this business file does not declare them. Generated support depends on the selected profile. The plain-language glossary covers all 13; UI meta types have separate candidate standing.

An AlchLang Entry is a named callable boundary for a Query or Operation and carries an access requirement. It is not a fourteenth backend meta type. A profile is also separate: it selects how supported declarations are built and run.

Step 5 · The language

Declare those parts in AlchLang

AlchLang is the .alch language for this supported business model. These excerpts are from the actual Customer Success source. Open each step to see how one declaration connects to the next.

1. Shape the account and give the stored copy an identity 
module CustomerSuccess version 1

enum RenewalAction:
  value Renew
  value AdoptionReview
  value SupportReview

value-object AccountSnapshot:
  accountId UInt64
  version UInt64
  licensedSeats UInt64
  activeSeats UInt64
  openEscalations UInt64
  activities List<Activity,16>

entity StoredAccount:
  accountId UInt64
  value AccountSnapshot
  identity accountId

The full source declares Activity too. The Enum limits the result to three choices, the Value Object describes the account, and the Entity gives a saved copy an identity. The rule AccountNumbersValid: declaration checks IDs, versions, seat counts, and activities with a Boolean expression.

2. Compute the score and choose the action 
calculation HealthScore:
  pure
  input account AccountSnapshot
  result UInt64
  rounding floor
  expression account.activeSeats * 100 / account.licensedSeats + fold(account.activities,0,total:UInt64,item:Activity => total + item.adoptionPoints)

policy SuggestedAction:
  input account AccountSnapshot
  result RenewalAction
  ordered-cases:
    escalated when account.openEscalations > 0 -> Support()
    underused when account.activeSeats * 2 < account.licensedSeats -> Adoption()
    otherwise -> Renewal()

The fixture produces score 95 and action Renew. The full source declares the action Enum and its helper Calculations.

3. Enforce the review and read the stored account 
operation EvaluateRenewal:
  input account AccountSnapshot
  input request ReviewRequest
  output RenewalReview
  enforce RenewalEligibility(account=account,request=request)
  return ToRenewalReview(account=account,request=request)

query ReadAccount:
  input accountId UInt64
  source stored StoredAccount
  output optional<AccountSnapshot>
  where stored.accountId == accountId
  project stored.value
  on-missing return none
  on-unavailable fail account-unavailable

RenewalEligibility rejects stale versions, mismatched actions, invalid cited context, or a declined choice. A Mapping then constructs the complete review:

mapping ToRenewalReview:
  input account AccountSnapshot
  input request ReviewRequest
  target RenewalReview
  total true
  field reviewId <- request.reviewId
  field accountId <- account.accountId
  field accountVersion <- account.version
  field healthScore <- HealthScore(account=account)
  field action <- SuggestedAction(account=account)
  field discussion <- request.citedContext.answer
  field citations <- request.citedContext.citationIds
  field evidence <- request.citedContext.evidence

total true requires every target field. The full source shows the eligibility policy and its Rules.

4. Save the review through a protected Operation 
operation ReviewRenewal:
  input request ReviewRequest
  output RenewalReview
  read account from CustomerSuccess.ReadAccountEntry(accountId=request.accountId)
    on-missing reject account-missing
    on-unavailable fail account-unavailable
  call accepted EvaluateRenewal(account=account,request=request)
  transaction RecordReview:
    atomic-participants StoredRenewalReview
    create stored StoredRenewalReview:
      reviewId <- request.reviewId
      value <- accepted
    on-unique-conflict reject review-already-recorded
    on-proven-rollback fail storage-rolled-back
    on-unknown-commit fail outcome-unknown
  return stored.value

The Entry makes the Operation callable and states its access requirement:

entry CustomerSuccess.ReviewRenewalEntry:
  invokes CustomerSuccess.ReviewRenewal
  interaction request-response
  access:
    authenticated customer
    permission renewal.review
    auth-resource renewal
    auth-action review
    auth-scope customer-success

The HTTP profile maps it to POST /api/renewal-reviews; the route does not grant permission.

Step 7 · Evidence

Run it and read what happened

From the Lab root in the configured Linux environment, build once and run the focused Customer Success test:

node workspaces/products/craft/implementation/run.mjs build
CRAFT_PORTFOLIO_LIBRARY_ROOT="$PWD/workspaces/products/craft/implementation/cli/examples/technical-profile-source" \
  node --test --test-name-pattern=generated.customer-success.domain \
  workspaces/products/craft/implementation/verification/portfolio-business-applications.test.mjs

The test checks and generates the application, records the account, submits a review, reads the saved value, and exercises rejection cases. The current focused run passed: 1 test, 0 failures. Its test cases expect score 95 and action Renew. Account version 2 is rejected with account-version-stale and is not saved. Permission denial and command replay are also checked.

This is local behavior evidence with fixture Auth and SQLite. Live CRM data, production identity, hosting, model quality, and deployment require separate qualification. The connected cited-answer path has additional checks in the application example.
