## Ownership

An Operation declares its contract: input/output, read/write subjects, required
Rules and produced Events. A separately named Alch realization selects that
Operation and declares its typed value connections. It is not another domain
meta-type or a new provider capability. Runtime profiles select infrastructure;
they cannot fill missing business choices.

## File-based check, build and verification

```sh
alchlang check commerce.alch
alchlang check commerce.alch --application-bindings inputs/application.json
alchlang build commerce.alch --out commerce-generated
alchlang verify commerce.alch --out commerce-generated
```

The default companion is `commerce.alch.application.json`. Its closed transport
schema is `alchlang.application-file/v1-candidate`, containing the exact
`source_sha256`, references named `bindings`, `interpretation`, `execution`, and
an explicit `evidence` reference array. Each reference uses the existing
`path`, `sha256`, `size_bytes`, `current: true` format. Paths are relative to the
selected source directory, including when the companion lives in a subdirectory.

Optional references are `persistence`, `messaging`, `external_api`, and
`observation`; `runtime_profile` explicitly selects an authored runtime profile.
These files carry existing binding contracts unchanged. They do not create
meaning, acceptance evidence, provider choices or executable Operation bodies.
For authored realizations, the execution selection omits `operations` and
`value_compositions`; both are derived from source.

The loader checks exact bytes, confines relative paths, rejects symlinks,
requires regular files, and bounds each selected file to 16 MiB and the selected
input total to 64 MiB. It reads only the selected evidence. The check compiles
the source graph and plans artifacts in an owned temporary directory, then
rechecks inputs and removes the directory. No provider is executed and no build
destination is written. Results distinguish `executable` checking from
`whole-application-artifacts` checking when observation input is supplied;
`runtime_guarantees_observed` remains false in either case.

Build requires a new destination under an existing real directory. It refuses
existing files, directories and symlinks; there is no overwrite flag. Generated
code retains its compiler-defined paths. Domain graph sources, formed contracts,
input digests and traces are placed under `.alch/`, with any whole-application
binding artifacts under `.alch/whole/`. Whole-application builds consume the
checked DomainSpec application composer, emitting joined domain/integration
code, typed request handlers and the native project configuration. The artifact
index records paths and digests without duplicating generated code in metadata.
The plan digest is included in the report, trace and build manifest.
`.alch/manifest.json` is written last as
the completion marker. Inputs are rechecked before and after sealing. On failure,
cleanup removes unchanged files and directories created by that build, preserving
foreign additions, replacements and edits.

Verify independently regenerates expected bytes from the current source and
companions. It checks exact file coverage and bytes, including metadata, and
rejects missing, extra, altered or symlinked output. Editing both a generated file
and its recorded digest cannot make verification pass. Verification is read-only
with respect to the output directory; neither command executes providers.

These commands now generate the graph-derived TypeScript provider application,
and the bounded test path natively compiles it and exercises its signed inbound
adapter. The public reference-pack path derives persistence, messaging and
external-API bindings from authored declarations; those backend documents are
absent from the companion. PostgreSQL, NATS and outbound HTTP behavior remain
unobserved, so the artifacts are not a qualified durable provider or a complete
deployed application. The bounded I07 semantic witness and limits are recorded
in `L1-COMPLETION.md`.

The block expresses dependencies, not an imperative instruction list. No loops,
assignment, embedded host code, inline propositions, generic call mechanism or
automatic ordering-by-source-position is introduced. Multi-Operation composition
remains a Workflow responsibility. Existing Mappings own field projections.

## Required information

The compiler must obtain each required choice explicitly or derive it only from
an unambiguous existing typed declaration:

| Connection | Information preserved |
| --- | --- |
| Selected Operation | Exact identity and declared input/output types |
| Input value | Named input binding; not an implicitly selected entry point |
| Reads | Declared source/Query, explicit key arguments, result identity and cardinality |
| Guard arguments | Existing Rule identity and exact input/read/mapped values supplied to it |
| Mapping arguments | Existing Mapping identity and all declared input values |
| Writes | Declared target, explicit create/replace mode and exact value source |
| Events | Declared Event and exact payload/identity/occurrence value sources |
| Result | Exact value source matching the Operation output |
| Settlement | Existing atomicity and continuation choices, without provider inference |

Factories, explicit validators and FormalClaim interpretations retain their
existing independent obligations. Selecting a realization does not prove a
FormalClaim, construct a valid Entity merely by mapping it, or grant acceptance.
The author must not supply compiler-generated selectors, artifact digests or
internal action-contract JSON as substitutes for the missing Alch surface.

## Discriminating example

The existing application scanner now accepts this separate declaration:

```alch
realization SubmitOrderExecution:
  operation SubmitOrder
  input request
  read current <- Order key request.id
  guard EligibleOrder(order <- current)
  write Order replace <- request
  result <- request
  atomicity state-and-outbox
  continuation awaited-settlement
```

The structural model also retains named connections to declared Queries and
Mappings, for example `query current <- FindOrder(id <- request.id)` and
`map summary <- OrderToSummary(order <- request)`. These are declaration
references, not arbitrary calls. Query absence/cardinality and path types are
not proven by parsing. The typed checker rejects implicit optional unwrapping,
collection traversal and type coercion. Raw Entity
reads and Query references remain distinct, not interchangeable substitutions.

### Optional Query results

A Query remains optional unless its realization explicitly declares an absence
failure. The policy names the Query **value binding**, not the Query declaration:

```alch
  query current <- FindOrder(id <- request.id)
  on-absence current fail ORDER_NOT_FOUND
  map copied <- CopyOrder(value <- current)
```

This connects the existing backend `require-present` policy and explicit failure
code. It is not an imperative branch. Clause position does not establish execution
order. If the Query returns no result, the Operation fails before effects are
committed and attempts rollback. A present result supplies the downstream value;
multiple results still fail with `QUERY_CARDINALITY`. Rollback uncertainty retains
the existing settlement semantics.

Without `on-absence`, the result retains its optional wrapper. No error code,
default value or unwrapping is inferred. The clause requires an optional Query
binding and one explicit code of 1–128 uppercase ASCII letters, digits or
underscores, beginning with a letter. Unknown bindings, duplicate policies,
Mapping/input bindings and list results reject. Partial Query projections remain
partial after presence checking: only selected fields can be traversed, and the
projection cannot substitute for the whole Entity. Existing Rule, Mapping and
factory validation obligations are unchanged.

Event inputs are explicit and distinct from ordinary domain values:

```alch
  event-input submitted OrderSubmitted
  event OrderSubmitted <- submitted
```

`submitted` supplies the occurrence/payload input expected by the existing Event
constructor, not an already constructed Event. The selected Event declaration
owns occurrence and occurred-at requirements. Generated timestamps still require
the explicit runtime clock dependency. The typed checker keeps Event inputs
opaque: no implicit field traversal, Entity conversion or replacement of one
Event identity with another. Unused Event inputs reject.

All three declarations (Operation, realization, runtime profile) have distinct
ownership. No new canonical graph relationship is implied by the `<-` notation.
Executable preparation uses `alchlang.application-execution/v2-candidate` when
realizations are authored. Its selection must omit both `operations` and
`value_compositions`: these are derived from the realization. Even identical
or present-but-undefined supplied values reject as overrides. The compiler
selection for named calls is explicitly `domainspec.reconciled-compilation/v2-candidate`
with profile `domainspec.reconciled-typescript/v2-candidate`; the existing v1
profile is not silently upgraded. Sources without realizations retain existing
behavior.
`deriveApplicationRealizationCompositions` separately derives named Query/Mapping
bindings and their effect action. Query source slots preserve the declared
qualified Entity source; several Queries may share that collection slot, but
keyed Entity reads cannot share it. Queries retain optional/list cardinality;
no absence error code or implicit unwrapping is invented. Partial backend Query
projections remain distinct from whole Entity values. Mapping outputs remain
projections rather than construction or invariant proof.

The project-level adapter now generates Query/Mapping connections under that
explicit v2 selection. The legacy profile still rejects them as
`APPLICATION_REALIZATION_UNSUPPORTED`; it cannot receive only their effect
action while discarding the calls. Read keys depending on another read or a
computed value remain unsupported. The native composition test runs through
the Alch project adapter and public backend APIs, including exact source-graph
checks, then compiles and executes all generated TypeScript. This proves the
internal source-to-project seam, not an installed public CLI build or provider
durability. No connection is dropped or replaced with a direct Entity lookup.

For the existing fixture, the connections mean:

- request.id supplies the stored Order lookup key;
- the stored Order supplies the EligibleOrder argument;
- the incoming request supplies the replacement Order;
- the incoming request supplies the returned value.

These are not interchangeable. An eligible stored Order and an ineligible-looking
request still follow the explicitly selected stored-value guard; reversing those
values must not cause the compiler to silently move the guard to the request.
This example preserves the existing synthetic fixture behavior; it is not a
default business rule for all applications.

## Typed connection checking

`application-realization-types.ts` consumes the current Rule projection and
resolves authored paths to exact ontology properties. Read keys must match the
Entity identity type; Query/Mapping arguments must match declared inputs; guards
must match projected Rule parameters; writes and results preserve nominal types.
Public contracts retain Interface and contract identities and cannot substitute
for Entities. Identity references cannot implicitly load Entity state. Normalized
root-name collisions reject. Preparation invokes this checker before action
derivation; type compatibility does not bypass unsupported execution boundaries.

No factory validity, Event occurrence construction, absence-handling policy,
Query execution order or transaction behavior is inferred from type compatibility.
The typed result remains an internal construction artifact, not an accepted or
executable application.

## Action derivation boundary

The typed checker now produces a frozen dependency DAG with separate input,
Event-input, transaction-boundary, Entity-read, Query, Mapping, Rule-guard,
write-validation, Event-construction, result-validation and commit-intent nodes.
Connections retain the selected Query/Mapping/Rule and their typed-contract hashes.
Value dependencies and the existing guard-before-write, write-before-Event,
result-before-commit barriers are explicit. Every declared value computation is
retained; an unused result does not license silently dropping its validation.
Layers describe dependency frontiers, not a concurrent execution schedule or
permission to reorder observable provider effects. No interpreter is introduced.

Graph nodes and dependencies are canonicalized independently of source line
positions. Named contracts, cardinality and value paths remain in the fingerprint.
It is a dependency identity, not a substitute for full source/currentness or
FormalClaim identity; preparation still binds the exact projection/source.
This graph prepares the backend extension: the current action contract has no
Query/Mapping evaluation slots, so those executable paths remain rejected until
the complete checked extension and generators are implemented.

The candidate backend contract now lives in
`../reconciliation-v1/profile-compiler-reconciliation/operation-value-composition-contract.json`.
Its separate `domainspec.operation-value-composition/v1-candidate` envelope
contains an Operation reference and named Query/Mapping bindings with existing
typed value expressions. Query source slots and absence behavior are explicit:
`preserve` retains the Query result; `require-present` is reserved for an optional
result with explicit precommit-failure handling. It does not change the source
Query cardinality and explicit absent-result outcome binding are exercised by
the public executable integration. The decoder still selects no default.

`impl/cli/src/typed-operation/value-composition.ts` currently validates only
closed inert input, limits, identifiers, distinct names/arguments and local
dependency cycles. It canonicalizes binding/argument order without treating that
order as execution order. It does not yet validate external roots, declaration
roles, types, read-slot coverage or exact graph custody. It is not a public
packaged generator feature; existing action v1 and the 132-source capsule remain
unchanged. Graph checking, selected-contract packaging and generator integration
are required before this can discharge I07's executable composition obligation.

The direct keyed-read slice derives the existing DomainSpec operation-action
contract from named input, read key, Rule arguments, create/replace writes,
explicit Event input slots and result connections. Atomicity and continuation
retain explicit source choices.
Existing public backend decoding and compilation still check the complete action.
Preparation enforces complete Operation coverage and exact graph/source custody.

This internal v2 envelope does not finish the public authoring flow: factories,
Rule interpretations, integration choices and safe source loading still need
their complete source-to-application wiring. No user-facing build completeness
is claimed from the action derivation alone.
