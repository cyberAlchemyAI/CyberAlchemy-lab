Craft: keeping system intent connected to code

A visual introductory article and a documentation library that explain the same model at different levels of detail.

Proposed reader-facing name: Craft. DomainSpec v2 is the former name of this product lineage. This is a research proposal, not a product release or a rewritten canonical definition.

One introduction, several routes into the system

The article should help a developer or technical founder understand what Craft does, why its parts exist, and which questions its checks can answer. The documentation should then help that reader perform a task, understand a concept, or look up an exact contract.

The central explanation is simple: a software requirement can change meaning as it moves through architecture, implementation and evaluation. Craft makes selected meanings and relationships explicit, binds them to supported implementation forms, and produces evidence about exact inputs and outputs.

Introductory article

Recommended title: Craft: keeping system intent connected to code.

Alternative: From a system specification to checked code.

Target: approximately 1,600–2,200 words, with focused diagrams and one existing example. Explain principles throughout; use the example to make each principle inspectable.

Documentation library

Separate learning, task instructions, conceptual explanations and exact reference. All pages share one declared documentation edition and link to the same contract and example sources.

Keep internal decision numbers and historical repository paths in the maintainer appendix. Show necessary executable names and schema versions where a reader needs them.

Two later articles can deepen the introduction: What a successful check actually tells you, and Changing a model without changing what it already means. They should have their own examples and distinguish current bounded implementations from broader research goals.

The introductory article

Write for readers who understand ordinary software development but have never encountered Craft. Define specialized terms when they first become useful.

Proposed opening

A requirement can be clear in a meeting and still become a different rule in code. Consider a service that accepts a job only when the requested capacity is strictly below the available capacity. One implementation uses <. Another uses <=. Both may look reasonable, but they express different decisions at the boundary.

Craft is a system for describing supported software concepts and keeping their meaning connected to implementation and evidence. A rule has an explicit predicate. An operation declares the information it reads and the effects it may produce. Their connection is declared too. Those choices become inputs to construction and checking, so a later agent or developer can inspect the intended boundary instead of reconstructing it from memory.

The article should explain the general mechanism at every step. The capacity example supplies evidence and boundaries; it does not replace the conceptual explanation or imply that every business process is already supported.

Use the existing capacity decision

Frame the fixture as a service deciding whether a compute request fits within an available capacity snapshot. This scenario framing is proposed editorial context; the underlying node contracts already exist.

Declared rule

requested_units < available_units

Operation: read the capacity snapshot; return Accept when the guard holds, otherwise Reject. The fixture declares no state writes and no external effects.

Boundary: this operation decides. Reserving capacity, launching work and persisting an event would require additional declared behavior.

A documentation library organized around reader needs

Use the four reader needs described by Diátaxis. Keep the visual article as the main conceptual entry point, with direct links into the appropriate documentation route.

Learn · guided tutorials

  • Understand and run the capacity-decision fixture.
  • Compile a specification and inspect the result.
  • Construct and verify one language target.
  • Run the compiled graph with explicit inputs.

Begin with TypeScript. Offer Python and Rust as subsequent routes. Keep database setup and Lean installation outside the first successful path.

Do · task guides

  • Author a typed Rule or Operation.
  • Add a permitted relationship.
  • Choose an implementation language and profile.
  • Diagnose source or target drift.
  • Read a receipt and its coverage.
  • Certify a compiled graph.
  • Use a particular durable provider.

Understand · explanations

  • Meaning, role, realization and instance.
  • Relationships and composition constraints.
  • Deterministic construction and explicit inputs.
  • Static, runtime and formal evidence.
  • Craft within CyberAlchemy Lab.
  • Supported integrations and their open joins.
  • Conservative graph extension and the candidate checker.

Look up · exact reference

  • Backend types and formation contracts.
  • Relationship direction, endpoints and constraints.
  • Language realization catalog.
  • JSON schemas and expression grammar.
  • CLI commands, arguments and failure behavior.
  • Receipts, certificates and result states.
  • Provider-specific guarantees and dependencies.

Give every reference page the same useful structure

Start with a plain explanation. Then show the exact contract, required fields, one valid example, one rejected example, allowed connections, applicable implementation profiles and evidence limits. Place stable semantic IDs in an expandable technical panel. A reference entry should link back to the authoritative definition; explanatory prose must not silently redefine it.

Keep candidate tracks versioned

The relational theorem checker needs its own version selector, profile reference, API guide, trust assumptions, exact acceptance bindings and reproducibility instructions. Its captured Lab relations and Horn information predicates are different subjects from Craft’s backend relationship catalog. Neither set of counts should be presented as the other’s coverage.

A visual language that makes distinctions visible

Continue the existing article’s restrained KEP styling, typography and spacing. Use native HTML and SVG for technical visuals so text remains readable and relationships remain precise. Illustrations can support atmosphere; diagrams should carry the explanation.

Construction

Specification → compiled graph → selected realization → generated target.

Show the selected profile and exact inputs. Expand only the current step.

Execution evidence

Compiled graph + invocation → semantic execution → bounded receipt.

Show a separate comparison with a handwritten target where available. Do not imply generated code was executed by the interpreter.

Formal evidence

Exact compiled projection → selected proof/checking route → scoped certificate.

Keep the graph-certification path and extension-checker path visibly distinct.

Model evolution

Proposed extension → required obligations → checking → bounded review result.

Explain what existing meaning must be preserved and which premises the result assumes.

  • Use labeled colors plus icons or shapes; color alone should never identify a concept.
  • Keep connectors short. Put transition text in its own element rather than across a vertical arrow.
  • Distinguish declared relationships, typed references and process steps with labels and line styles.
  • Show planned integrations with an explicit status label. A dotted line without a legend is insufficient.
  • Offer an overview first, then selection-based detail. Avoid an all-connections graph as the default.
  • On narrow screens, turn flows into ordered cards; preserve direction and connector labels.

Build in this order

  1. Bind a documentation edition. Produce a claim and coverage matrix tied to selected definitions, catalog, CLI source, schemas, source epoch and candidate acceptance records. Resolve old baseline and status projections.
  2. Prepare the first tutorial. Use the existing capacity fixture. Establish a dependency-closed installation path, then capture the success, equality rejection and artifact-drift cases. Record exact prerequisites and outputs.
  3. Draft the introductory article. Write from the same claims and tutorial. Produce the small concept graph, construction flow, evidence panels and agent work sequence.
  4. Create the shared reference. Derive schema, catalog and command facts from selected sources. Write the plain explanations and examples manually. Preserve authority and source lineage.
  5. Add advanced guides. Separate in-memory execution, SQLite API, PostgreSQL CLI, Lean graph certification and versioned relational extension checking.
  6. Review the complete reader journey. Check semantic consistency, links, actual instructions, responsive diagrams and keyboard access. Ask newcomers to explain the boundary case and identify what each result establishes.

First delivery: the edition/claim matrix, one end-to-end tutorial, the introductory article, and reference pages for the four example types and two declared edges. Extend the rest of the library from that coherent slice.

Keep the documentation current

Maintain a content manifest that binds page claims and examples to exact source selectors and versions. Mark historical, candidate and supported material explicitly. Reference generation should expose changed fields and missing coverage. Store expected tutorial outcomes with the examples and refresh recorded outputs when their inputs change.

The quality target is observable: a new reader can explain Craft’s purpose, predict the equality decision, identify a declared effect, find the permitted endpoint of an edge, and tell which question a certificate answers. Set measured usability targets after observing an initial reader baseline.
