How the records fit together

“The experiment evaluates the export capability” sounds clear in conversation. A system record needs more precision: which experiment design or run, and which capability version? Does the link say what was evaluated, that evidence supports a claim, or that software was adopted? CyberAlchemy Lab keeps these meanings separate so following one connection does not accidentally answer another question.

A Definition states a term’s accepted meaning within an owner’s scope. Its scientific and formal wording governs that meaning; its plain-language and domain explanations help readers understand it. An Artifact Type sets requirements for records of a particular kind, linking meanings to a versioned machine format and its other required views. An artifact instance is one particular identifiable, versioned record. Accepting a type and accepting a record using it are separate authority acts. The Lab calls formal acceptance admission.

A Schema specifies permitted structure: kinds, fields, constraints and connection rules. A record that passes schema checks meets those checked structural requirements. Its evidence can still be weak, sources outdated or requested actions unauthorized. W3C SHACL illustrates how graph-structure checks can be explicit. This comparison explains one validation task; it does not establish that the Lab uses SHACL or that passing structure checks accepts a record’s meaning. [W3C SHACL](https://www.w3.org/TR/shacl/).

The Four-Facet Artifact Invariant applies to governed actions that create, change, route, validate, promote, implement or interpret load-bearing artifacts, state or meaning. Before such an action can govern downstream work, it must bind, create or record a missing facet as typed residue for each of four aspects: classification, schema, a view a human can understand and continue from, and a view a machine can parse or check. Missing aspects need their reason, owner, evidence and an explicit continue, defer or block outcome. The Canonical Representation Invariant separately requires one designated machine representation. “Canonical” here concerns its declared form and origin; it does not itself mean true or authoritative. Human explanations and convenience labels must not become competing master records.

Registries are catalogs selecting exact definitions and record contracts. Artifact Type Resolution identifies an accepted contract from an exact reference or a declared discriminator—a field and value that identify the type. It reports uncertainty or ambiguity instead of guessing from filenames. Older references may still resolve while another version is selected as current. If no reusable contract fits, an Artifact Type Request records the gap for review. The request is not a substitute for the missing accepted type.

A Relation Kind defines one kind of connection, its direction, permitted source–target kind pairs, required extra details and conclusions the link cannot justify. A Typed Relation is one connection between specific versions under that rule. The snapshot’s catalog contains 41 relation kinds and 550 allowed ordered pairs. “Ordered” means source and target are not interchangeable. A list of possible sources and targets does not permit every combination.

For example, member-of records membership, contributes-to records intended contribution, and evaluates identifies what was assessed. evidence-bears-on records how evidence relates to a claim, including the stated direction of support or opposition. These links cannot replace one another. The catalog explicitly permits Experiment Design and Experiment Run to evaluate Product, Product Capability, Product Thesis and Capability Realization Binding. Experiments therefore have permitted product connections as well as research connections; none implies a favorable result.

The Typed Connection Extension Rule specifies how permitted connections can expand. Reuse an existing relation kind when its meaning and constraints fit. Adding a source–target pair requires review and acceptance of a revised contract. Asking a different semantic question requires a distinct relation kind. The process preserves ownership, evidence, versions, lifecycle and challenge rights. Registering a new kind of endpoint—the thing at either end of a connection—does not grant it additional connections.

Non-collapse checks whether concepts describe genuinely different facts. An assignment can exist before permission is delegated. A capability can be declared before an implementation is adopted. An experiment can evaluate a product and fail. Formalization translates these distinctions into logical statements. A witness or countermodel is a specified case demonstrating the distinction under stated assumptions. Consistency checks instead ask whether the combined requirements can all hold together within the chosen theory.

The inspected assurance work covers sources for 183 selected definition identities and contains partial formal translations. It reports zero verified whole-definition proofs at that snapshot. A proof checker can accept a formal statement while the relationship between that statement and the intended definition still needs justification. Lean’s documentation helps explain that boundary. A successful check supports a claim about the Lab only with an adequate account of how the formal statement represents its source meaning. [Lean, Validating a Lean Proof](https://lean-lang.org/doc/reference/latest/ValidatingProofs/).

An ontology is a structured model of concepts, things and relationships. An Ontology Node represents a specific thing and revision. An Ontology Edge represents a particular Typed Relation or a connection explicitly declared within that ontology. A local connection does not become a global Lab relation merely by appearing in the graph. Representations and source records retain separate identities and authority; drawing an edge cannot authorize changing the source.

A Model Instance Binding similarly records how a local instance relates to a particular shared parent model while keeping their owners and authority separate. An Ontology Cut reconstructs one consistent recorded state from selected positions in its event histories. An Ontology View selects from that state for a purpose. A graph answering “what relates to lifecycle?” must identify its sources, coverage, exclusions, unresolved references and freshness. Completeness is measured against that stated scope, not every possible project object.
