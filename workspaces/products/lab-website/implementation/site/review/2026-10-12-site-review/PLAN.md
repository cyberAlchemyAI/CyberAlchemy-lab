# Whole-site review

12 October 2026

## Scope

Review the current website as a single public experience: product homepage, company story, research and culture, the introductory path, incident walkthrough, concept comparisons, all guide topics, all eight expanded essays, reference catalogs and exact records, practical guides, complete examples, Craft chapters, the robot-learning series, shared search, redirects, the response form, and static delivery.

The user requested a review. Findings and proposed fixes are the deliverable. This run does not publish the site, accept Lab records, or silently revise product claims.

## Review sequence and evidence

1. Inventory every delivered HTML file, route, local resource and shared control. Bind the run to the release manifest and source digests.
2. Walk representative user goals from the homepage, company story and research page into the model, practical material, software design and references. Record observed behavior separately from an expert judgment about clarity.
3. Inspect wording and technical boundaries across every authored surface. Compare high-risk claims with the selected formal sources and current repository content. A preserved record body is evidence of preservation, not proof of all prose.
4. Inspect every public page and chapter at desktop and phone widths, then review diagrams, formulas, expanded records and mobile navigation. Capture screenshots and measurements.
5. Exercise search with existing judgments and additional whole-site questions. Report the new questions separately because the earlier set includes authored aliases.
6. Scan representative visible states with axe, inspect keyboard and zoom behavior, and retain each incomplete finding. Automated checks do not establish screen-reader usability or complete WCAG conformance.
7. Check current packaging, repeatable build output, root and project-path hosting, offline navigation, redirects, metadata and local performance. Do not infer hosted field performance from localhost.
8. Produce prioritized findings with affected pages, evidence, recommended changes and explicit coverage limits.

## Evidence classes

- Browser observation: a recorded action, measurement, screenshot, announcement structure or request outcome.
- Structural check: an exact ID, digest, file, local link or formula relationship.
- Expert review: a reasoned assessment of clarity, visual hierarchy, repetition or reading flow. This is not participant evidence.
- Human review pending: actual newcomer task success, trust, comprehension and real assistive-technology operation.
- Hosting observation pending: real deployment, actual Safari/device sessions and field performance where unavailable locally.

## Research basis

- [WCAG 2.2](https://www.w3.org/WAI/WCAG22/quickref/): text alternatives, keyboard access, contrast, reflow, focus, target size and status messages.
- [NN/g task scenarios](https://www.nngroup.com/articles/task-scenarios-usability-testing/): realistic goals without revealing the intended navigation.
- [Diátaxis](https://diataxis.fr/): separate explanation, how-to, reference and tutorial needs where useful. This is guidance, not a mandatory classification for marketing or research pages.
- [Web Vitals](https://web.dev/articles/vitals): distinguish lab diagnostics from field distributions.

## Outputs

Local browser evidence: `website/output/playwright/ux-validator/20261012-whole-site/`, including run metadata, findings, console/network output, ARIA snapshots, screenshots, measurements, traces and a residue ledger. These files stay outside the deployed package.

Completion means all locally feasible review items above have evidence and a disposition. Findings need not be fixed to finish this review. Actual participant and assistive-technology observations remain separately identified follow-up evidence.
