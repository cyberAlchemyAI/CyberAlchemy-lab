# INC-1042 through the complete revised design

This is a design walkthrough of the existing synthetic example, not a newly executed incident or actual approval. Symbols P, R, C and W denote values computed later from actual frozen bytes; they are not fabricated operational receipts.

## 1. Capture what the investigator actually has

The agent investigates missing identifiers in Northstar's export. A real permitted Base capture selects exact Incident and Work meanings, context/source cut and their available standing evidence. The local completeness criterion is kept in a separate candidate-supplement population:

> For a fixed source snapshot S, account A, filters F and saved extraction E, every identifier required by S/A/F appears in E.

Its explicit parameters are S, A, F and E. The application binds `S-1042`, `Northstar`, `{status:active}` and `E-1042`. The example's declared filter interpretation is synthetic; a real integration needs the actual source filter contract. Field accuracy, duplicates, extra/foreign IDs, root cause, repair permission and incident closure remain excluded from this criterion.

An E2 local body cannot be called a current admitted E1 member merely because both hashes are correct. It stays a supplement or causes recapture/refusal if it claims to be the governing member.

## 3. Retain the task result, if selected

The investigator explicitly selects retention for the Work result. The export builds a closed member manifest containing exact `pack.json`, capture, report/lineage and required original evidence. Its raw-byte digest is R.

The host checks actual retention permission, scope, privacy and limits. It stores every required member and the exact root in the independent retained store, then commits the completion receipt. At this point, R identifies retained task knowledge; it is not an admitted shared criterion or completed incident.

The receipt is real only after the future host implementation performs and verifies the writes. Neither a Source proposal nor a local manifest proves this step happened.

## 4. Select reusable meaning separately

Suppose the investigator selects the general completeness criterion for shared review. Full Definition/v2 materialization contains the reusable statement, notation, applicability/exclusions, voices, sources, consumers, lineage and required assurance/profile evidence. Northstar/S-1042/E-1042 stay in the task application.

If retention linkage is selected too, the cohort includes the Source bound to R, optional Evidence Set and exact Work output revision. New Source/Work records are outside the retained root; they cannot be members that recursively hash R. If the reviewer wants only the shared meaning, task-retention targets are not silently added.

Freeze the selected complete dependency-closed cohort as C. Missing required profile standing, sources, carrier representation, owner scope or semantic evidence blocks that affected review route; prose fields are not fabricated to force completion.

## 5. Stage the exact review

The host stager verifies the actual operator/principal/key/scope policy for C. It creates metadata and stable core-file bytes using the selected host helpers. It publishes a new immutable workspace W with those exact bodies, schemas, metadata, cores and independently selected routing.

The new channel authenticates against W's actual policy. `change.prepare` independently recomputes/compares the targets and cores, then `proposal.review` revalidates the complete original proposal and ordered cohort. Its generated object refs belong to W. Reusing object refs from an older workspace is refused.

The visible result is a pending exact all-or-nothing review. It contains no actual owner outcome. The same human principal appearing in several role routes does not merge those role obligations.

## 6. Apply only actual authorized outcomes

When the separate actual owner/profile/representation prerequisites and exact accepted outcomes exist, the native publisher rechecks C, expected head, permission, generated consequences and R's completed required closure. It commits one authorized coherent epoch. Rejection or incomplete evidence does not permit application.

A crash before the epoch commit leaves retained unlinked bytes and possibly a pending review. A lost response after commit is reconciled through the actual host operation/epoch receipt, not by generating new identities or retrying under a fresh key.

## 7. A different agent reconstructs the knowledge

The first Session ends. A new authorized Session resolves the selected Work revision, its exact Source and the permitted `lab-retained://store/sha256/R` locator. The host resolver checks the complete receipt, root and every required member, then verifies the Pack and entry selectors. It returns the exact original Pack P, including the original FAIL and open exclusivity question.

If one required snapshot member is missing, the result is `reconstruction-incomplete` with that exact binding. A matching R alone cannot produce success. If the old access permission expired, the new Session needs its own valid read permission; durable bytes do not prolong a lease.

## 8. Later work changes evidence without rewriting meaning

A separate Work/producer supplies `E-1042-retry` and a recorded assessment reporting all 12,000 identifiers present. A new application/Pack revision keeps the original failure and binds the new evidence. The general criterion is unchanged; no new shared Definition is needed for the retry.

A fresh use observation over an unchanged frozen Pack may still block a new consequential use if current source/profile/permission conditions differ. A changed intended use or input requires the applicable new frozen revision. Even a valid presence PASS leaves exclusivity, root cause, repair permission and incident closure to their own rules and evidence.
