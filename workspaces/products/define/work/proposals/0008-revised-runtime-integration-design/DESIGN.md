# System design

## 1. Scope and six design views

| View | This design answers |
| --- | --- |
| Purpose and user outcome | One task Pack, selected reusable meanings reviewed through the Lab, later knowledge recoverable by a fresh Session |
| Context and external dependencies | Selected Lab source/provider, context/ontology, actual caller permission, compatible carrier/profile/owner routes and native publisher |
| Components and interfaces | Three Define responsibilities, one concrete adapter and one host-owned successor boundary |
| Information and state | Exact classified capture, frozen Pack, independent use observations, review cohort, immutable retained closure and host epoch |
| Behavior and interactions | Preparation → optional materialization/retention → new review workspace → pending review → actual authorized application → reconstruction |
| Deployment, operation and assurance | Isolated successor CLI/host selections, separate private custody, no-replace publication, bounded reads, journal inspection and phased qualification |

This is an implementation design. It does not revise or admit the reviewed Definition, Definition application, Definition Pack, Define or profile meanings.

## 2. Ownership and dependency direction

| Owner | Responsibility | Effect boundary |
| --- | --- | --- |
| Human / ephemeral agent interaction | Supply Goal/Intent/use, concepts and attributable handling/supplements; explicitly select materialization/retention | Suggestions and submission do not constitute semantic admission |
| Define capture/normalization | Select permitted original bytes, classify their origins, preserve exact selectors and source observations | No permission, current standing or epoch membership invented |
| Define pure preparation | Construct/check one Pack; embed applications, task values, assessments and gaps | No domain Method execution or implicit meaning change |
| Define export/handoff | Publish new local immutable output; select complete reusable materialization; submit exact handoff inputs | No owner identity, policy issuance, signing or governing write authority |
| Lab host successor | Scoped staging, exact native core construction/validation, independent review preparation, persistent byte custody and resolution | Operator permission remains distinct from actual owner decisions |
| Existing native Governance/publisher | Verify actual required owner effects, commit the authorized coherent epoch, recover/inspect uncertain effects | Only this qualified boundary changes governing state |
| Fresh authorized reader | Resolve selected Work/Source/Evidence records and exact retained bytes under a fresh read permission | A historic preparation report does not enable current consequential use |

Define depends on the selected host SDK/protocol contracts; the host's material store and stager do not import Define code. They accept a digest-closed manifest or selected carrier targets. The preparation core has no host I/O dependency. Source/provider/schema/code selections are explicit; highest-version-directory discovery is forbidden.

## 3. Implementation shape

Preserve `implementation/define-cli/v1/` and its legacy dispatcher/protocol unchanged. A separately selected successor entry is the proposed implementation target. Keep JavaScript interaction/delegation thin: it passes opaque original bytes or permitted frozen file references to the Python boundary. Python owns strict decoding, source hashing and new authority-record encoding. The host owns native core encoding, authentication, actual signatures and authority verification.

Choose internal files around three responsibilities after behavior/reuse evidence. Existing disposition/readiness and no-replace publication mechanics are reuse candidates only where their selected contracts match. Do not maintain competing semantic validators or recreate host hashes in JavaScript.

The required host successor extends the selected API17 family with:

1. A narrow local operator boundary for `stage-review`, `retain-package`, `read-retained` and `inspect-local-operation`.
2. A scoped review/preparation policy branch whose authority binding comes from the independently selected current operator configuration, not the historical one-shot document.
3. A retained-reference resolver for the existing Source, Evidence Set and Work fields used in this path.

These are proposed local extension operations, **not existing Lab public API operations**. Their structured contracts live in [handoff](REVIEW-HANDOFF.md) and [reconstruction](RECONSTRUCTION.md). Existing `change.prepare`, `change.validate`, `proposal.review` and branch-owned inspection remain the protocol operations for actual candidate validation/review. No generic upload, network storage service, plug-in backend registry or new governing ledger is introduced.

The successor is a new frozen package/profile with its own complete code/import/schema/source guard. Existing `type(service) is Service` and source pins cannot be bypassed by injecting a new object into API17. All affected original guards, authenticated context construction and trusted-source selection must be rebound coherently in the successor. The launcher changes only at explicit qualified adoption.

## 4. Concrete adapter and source population

One `cal.define.lab-adapter-selection/v1` selects a local stdio host installation, exact host/extension/profile/schema/dependency bindings, operation mapping, external credential locators, current-source selection contract and limits. Snapshot preparation consumes a captured bundle directly; it is not a second live backend discovered at runtime.

| Capture population | Permitted standing |
| --- | --- |
| Host-selected member | Exact captured standing under one verified source cut and declared encoding |
| Local supplement | Attributable candidate content or task values; no inherited admission/currentness |
| External evidence | Exact producer/method/input/receipt bytes with their stated execution and claim scope |

A local copy claiming to be a selected host member must match the actual host binding. E1 context plus E2 body is not a coherent admitted E1 source. Refuse conflicting membership or recapture. Preserve unavailable refs and affected uses as gaps rather than substituting a later body.

Obtain Context and selected Ontology Views through the host's permitted interfaces. Views are derived representations, not new admission effects or inferred global edges. Request actual machine Session resources only under a policy that permits them. API17 metadata authentication explicitly has null agent/session/assignment refs; the review operator branch must preserve that posture unless a separate genuine machine context is verified.

## 5. Pure preparation behavior

`prepare(request, captured_bundle)` receives explicit attributable handling. It returns a frozen Pack plus deterministic report/view/lineage, or blocking diagnostics without a falsely complete Pack.

Exactly one current disposition per declared concept:

- `reuse`: exact captured current admitted meaning and applicability;
- `specialize/application`: unchanged meaning with declared parameters;
- `specialize/meaning-change`: explicit unadmitted semantic delta;
- `propose`: embedded task-local working meaning;
- `open`: explicit question/reason/use/continuation, possibly blocking a later use.

No standalone Definition is generated merely to bind task values. Full Definition/v2 materialization occurs only for selected reusable meanings, with exact new/successor identity, complete voices, parameter/source/consumer fidelity, field lineage and applicable assurance/profile requirements. A selected target whose current carrier/representation cannot be expressed is refused pending the required provider/representation successor; no old carrier is substituted.

Parameter maps bind exact meaning clauses, names/types/required values and applicability. Definition/v2 is not silently extended with a generic top-level parameter field. Model extraction alone supplies no governing parameter authority. A generic JSON filter object does not prove the meaning of the source system's filter keys.

Define verifies imported assessments' application/input/producer/method/evidence bindings. It never turns caller counts into a completed Evaluation or executes arbitrary supplied formulas. The synthetic INC-1042 result remains synthetic.

## 6. Frozen content and use observations

The Pack contains preparation-time readiness only. A later `cal.define.use-observation/v1` binds exact Pack digest, unchanged intended use, fresh source/profile/scope observations, applicable obligations and evidence. It can refuse a stale use without editing the Pack.

Changed selected input, intended use, payload, concept set or meaning creates the applicable new frozen revision with lineage and any required new assurance/review. Refreshing an observation is not a way to reuse approval for changed content. Governing application is always rechecked by the actual host at its effect boundary.

## 7. State progression and joins

| State | Entry evidence | Next boundary |
| --- | --- | --- |
| Prepared locally | Frozen Pack/report and exact capture; possibly open concepts | Inspect, revise, select materialization or retention |
| Retained bytes complete | Exact root plus all required members and host completion receipt | Prepare Source/Evidence/Work targets; no admission yet |
| Review workspace ready | Complete selected bodies/metadata/cores/routing/policy, new immutable workspace and exact pins | Host independent change validation and review |
| Pending owner review | Exact all-or-nothing cohort independently revalidated | Actual required independent owner outcomes |
| Published governing epoch | Qualified host receipt and selected-pointer commit | Fresh selected views/read-back |
| Reconstructed | Fresh permission plus exact required retained closure and selectors | Inspect historical knowledge; separately assess current use |

Retention and review are separate joins. A meaning-only review need not retain the task Pack. A retention-only Work result need not materialize a shared criterion. If one final cohort selects both, retained bytes are completed first so Source targets can bind a real root; the full dependency-closed target set is then frozen and reviewed together.

## 8. Local extension invocation and permission

The host extension runs through the selected local operator entry, using the host's own authenticated channel and external policy selection. The caller never supplies a trusted context object. A fresh host nonce proof establishes key possession; an independent current installation/operator policy establishes which principal/key, scope, operations, cohort/package and periods are allowed. Actual native owner outcomes remain separate. Missing operator selection refuses; fixture key generation is not a fallback.

New local controls use closed JSON with explicit operation, request ID, idempotency key, exact software/policy/source binding, operation-specific exact bindings and byte limits. Control JSON is at most 1 MiB. Original material is supplied as ordered length-declared byte buffers, captured and hashed once; aggregate transfer is bounded. The local extension may use a bounded binary stream after its authenticated control frame; it does not disguise 16 MiB bodies as an existing 1 MiB API request. A read returns one verified buffer with exact length/digest; client acceptance requires the full buffer and successful completion, never a partial prefix. This is an explicitly new local transfer contract, not an assumed chunk API.

Every operation rereads/revalidates selected permission, revocation, expiry, source and required custody bindings at entry and immediately before commit/return. Long-term immutable bytes do not preserve an expired access grant. Requested deadlines can only narrow the selected periods. Cleanup releases only owned invocation resources; durable roots and unknown residue remain inspectable.

## 9. Source publication and later agent context

The existing qualified publisher commits an immutable dependency-closed epoch and atomically selects its current pointer under the writer lock/expected head. Registry/index/drift/Context/Ontology projections are derived from that selected epoch. Existing representation, profile standing and consumer compatibility gates remain mandatory.

Source/Evidence/Work records refer to retained bytes through the specified resolver. Filesystem custody alone is not Project State; only an actual selected governing record links the retained result into Project State. The next agent is newly instantiated. Its long-term knowledge comes from that state and its derived views; its Session short memory ends with the Session.

## 10. Compatibility and excluded behavior

Legacy `run/chat/compile/session` commands use their original selected handler, stdout/stderr/exit protocol and numeric contracts. New Pack compilation returns unsupported before output/effects. No automatic old-store migration, silent parameter extension, domain execution, follow-up work generation, incident closure, new semantic owner appointment or default launcher switch is part of preparation.

The [contracts](CONTRACTS.md), [handoff](REVIEW-HANDOFF.md), [reconstruction](RECONSTRUCTION.md) and [delivery review](REVIEW.md) specify the remaining exact joins and evidence gates. Completing these design contracts does not supply real operational credentials or qualify software that has not been implemented.
