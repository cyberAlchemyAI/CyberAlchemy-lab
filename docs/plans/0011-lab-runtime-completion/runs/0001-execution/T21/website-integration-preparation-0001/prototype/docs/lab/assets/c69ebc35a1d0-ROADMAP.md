# CyberAlchemy Lab roadmap

Status: **proposed roadmap for review**. Baseline inspected: **2026-10-07, repository D75**.
Authority effect: **none**. This document sequences work; it does not admit a package or authorize its execution.

The [complete milestone and implementation analysis with DAG plan](plans/0009-lab-integrated-roadmap/PLAN.md)
decomposes this roadmap into task contracts, evidence gates and dependency waves.

## Destination

CyberAlchemy Lab should let humans and ephemeral Agents turn intent into governed work, produce traceable evidence and durable lessons, update Project State through exact authority, and reconstruct fresh Context and Ontology Views for subsequent sessions.

The **Lab Product** provides that repeatable capability. The **migration Project** delivers a bounded transition from selected CyberAlchemy-v2 material into the Lab. Completing an import, a runtime implementation, or the migration Project does not by itself prove Product value or establish a stable release.

The complete operating loop is:

```text
Intent -> resolution and scoped work -> Define / Design / Plan
       -> authorized human or Agent work -> Implementation and observations
       -> evidence and assessment -> reviewed admission / revision / withdrawal
       -> Project State and independent semantic / governance histories
       -> rebuilt Context / Ontology Views -> next ephemeral session

Failures and challenges -> assessment -> operational lesson
                       -> later lesson application -> outcome assessment
```

These arrows describe workflow order. They are not declarations of global Relation Kinds. Implementation belongs in the loop; declaring intent does not establish implementation or satisfaction.

## Five milestones

| Layer | Milestone | Result visible to the user | Exit condition |
| --- | --- | --- | --- |
| **L0** | Foundation and controlled proof | Inspect admitted state; demonstrate one exact local transaction, replay and ephemeral context. | Exact contracts, implementation and scoped proof exist. Established for the admitted v1/D74 envelope. |
| **L1 — next** | Repeatable real local operation | Finish one real Work cycle; admit its selected results; reconstruct them in a fresh session after another admission. | Reviewed source-profile continuity, measured replay behavior, real workflow evidence, restart/recovery and explicit local/repository authority boundaries. |
| **L2** | Integrated work and learning | Engineering and research work connect to Product/Project context; failures become assessed lessons that can be applied later. | Representative workflows exercise the relevant contracts and exact relations, including a later lesson application and assessed outcome. |
| **L3** | Coherent ontology and controlled migration | Explain meaning, authority, provenance, implementation, evidence and gaps for the selected Lab scope. | Deterministic projections, exact source mappings, challenge/lifecycle joins and selected migration closure are evidenced. |
| **L4** | Usable Product and stable release | An operator can install, use, recover and upgrade a bounded Lab product; a pilot shows useful outcomes. | Exact release package meets the stability prerequisites and receives the owner release decision. |

Milestone closure order: **L0 -> L1 -> L2 -> L3 -> L4**. Ontology mapping and Product acceptance design can begin earlier where their inputs exist; the DAG records these dependencies. Ontology queries and selected source migration can support earlier layers. L3 establishes their broader integration and declared coverage; it is not the first time either is used.

### L0 — Foundation and controlled proof

**After this layer, we know whether** exact authority, deterministic state and ephemeral context can support a bounded operational transaction.

- **Minimum working unit / included scope:** admitted operational roots and contracts; one reviewed implementation; isolated transaction, fresh-process replay and session closure. This proof already exists within the v1 envelope.
- **Outcome / risk reduced:** inspectable state and attributable changes, without treating a view or a session as durable authority.
- **Cost drivers:** contract alignment, exact source capture, transaction generation and validation.
- **Exit evidence / decision:** D70–D75 admissions and v1 validation establish their stated scopes. The v2 receipt supplies additional candidate evidence, not v2 admission.
- **Deferred:** a permanent operator/store, repeatable repository promotion, complete work workflows, complete ontology coverage and stable release.

### L1 — Repeatable real local operation

**After this layer, we know whether** the Lab can continue trustworthy work as authority changes, without rebuilding the executable for every admission.

- **Minimum working unit:** one real Work cycle followed by a new admission, process restart and a fresh Agent session that reconstructs the approved result.
- **Included scope:** independently versioned, reviewed source-profile selection; explicit old-store compatibility/migration behavior; measured replay and, where justified, verified acceleration; exact local transaction and repository promotion boundaries; one selected evidence/lesson record persisted through review.
- **Outcome / risk reduced:** the user can perform the next piece of work without losing history or reading stale authority. A local store does not silently become repository authority.
- **Cost drivers:** continuity design, replay measurements, regression evidence, operator configuration and selected source-reference repairs.
- **Exit evidence:** exact before/after profiles and histories; proof that frozen packages remain unchanged; observed operation timings; fresh-process replay and recovery; approved real records; expired session memory and reconstructed next-session context.
- **Promotion decision:** review the revised package and realistic example, then decide its exact implementation/profile effects together where appropriate. Provisioning and adoption require their explicit scope; deterministic admission consequences require no extra bookkeeping approval.
- **Deferred:** full workflow coverage, broad migration, network services and Product-scale operation.

### L2 — Integrated work and learning

**After this layer, we know whether** the contracts form a usable work system and whether lessons can improve later work.

- **Minimum working unit:** one engineering workflow and one research/experiment workflow, plus a failure -> lesson -> later application -> outcome assessment sequence.
- **Included scope:** Intent/resolution, goals, Product and Project context, scoped Work, Define/Design/Plan, Implementation, evidence and satisfaction assessment; declared experiment connections to research and other permitted endpoints; human/Agent actors, delegation, assignment, actions and tools; classifications, Failure Modes/Occurrences, Incidents, Challenge Contracts/Events, reflections and Operational Lessons.
- **Outcome / risk reduced:** inspect what was intended, executed, observed, accepted, learned and subsequently applied. A generic record writer is not treated as evidence that every workflow works.
- **Cost drivers:** workflow orchestration, carrier/schema integration, relation coverage, permission boundaries and assessed examples.
- **Exit evidence:** exact records and valid declared relations for representative cases; traceable inputs/outputs; challenge disposition; later lesson application and assessed outcome. Selected, applied, compliant, beneficial and causally effective remain separate claims.
- **Promotion decision:** admit the exact workflow implementations and necessary contract revisions; assess realization, adoption and outcome evidence separately within the declared effects.
- **Deferred:** exhaustive domain workflows, automatic lesson promotion and broad autonomous operation.

### L3 — Coherent ontology and controlled migration

**After this layer, we know whether** the selected Lab scope can be reconstructed and explained coherently across source meaning, authority, implementation and evidence.

- **Minimum working unit:** one declared domain slice with exact artifact-to-Node and relation-to-Edge mappings, lifecycle/challenge joins, and a selected CyberAlchemy-v2 import with source-to-Lab traceability.
- **Included scope:** reuse/adapt existing ontology components; Authority, Provenance and Lifecycle queries; declared local edge namespaces; independent semantic/governance histories, Cuts and Views; coverage and freshness reports; selected byte inventories, import dispositions and unresolved-gap accounting.
- **Outcome / risk reduced:** the user can ask what a subject means, why its state counts, where it came from, what implements it and what remains unknown. Imported evidence cannot silently become authority.
- **Cost drivers:** adapter fit, namespace/identity mapping, exact revisions, source reconciliation and coverage obligations.
- **Exit evidence:** deterministic rebuilds and cursor/digest parity; separate global Typed Relations and ontology-local Edges; challenge joins; complete disposition of the selected migration inventory. Broader coverage remains explicitly bounded.
- **Promotion decision:** review exact mappings, adapters, selected imports and any required extensions. Source retirement or cutover needs an explicitly declared effect.
- **Deferred:** unselected legacy material, ontology Nodes for every inventory file, automatic source retirement and assumed transitive import closure.

### L4 — Usable Product and stable release

**After this layer, we know whether** the bounded Lab product is useful and operable enough to release as stable `v1.0.0`.

- **Minimum working unit:** a reproducible operator installation, one chosen user interface and a real pilot spanning work, review, recovery and fresh context.
- **Included scope:** coherent inspection/review UX; installation/configuration; upgrade/export/recovery; selected Capability Realization Bindings and adoption evidence; conformance/outcome measurements; release documentation; private/public boundary review; exact packaging and rollback evidence.
- **Outcome / risk reduced:** users can operate the Lab and understand its guarantees; Product value is assessed rather than inferred from implementation admission.
- **Cost drivers:** usability, packaging, operational verification, pilot support and release evidence.
- **Exit evidence:** accepted Product/architecture and authority boundaries; completed private/public review; deterministic validation of every admitted release artifact; pilot outcomes; exact release manifest and owner release decision.
- **Promotion decision:** stable release for the exact package. Publication/deployment effects must be stated in the chosen release scope.
- **Deferred unless selected requirements justify them:** multi-host writes, persistent network services, external integrations and multiple frontends. They are not automatic prerequisites for the first stable release.

## Immediate sequence: L1

1. **Design continuity.** Separate immutable executable packages from explicitly reviewed source profiles; specify profile selection, compatibility and transition. Preserve exact historical profiles and reject silent rebases.
2. **Measure replay.** Separate source capture, store replay, schema checks and context generation timings. Add verified caching/checkpoints only where the measurements justify them; retain full replay as the verification path.
3. **Prepare one reviewable successor.** Reconcile the selected scope's source gaps, bind exact package/profile/evidence and show an example of continued operation after another admission. Existing out-of-scope gaps remain visible.
4. **Review and admit the chosen effects.** One owner response can cover independent decision cores in one exact envelope. Generated State, history and bookkeeping consequences follow from that transaction.
5. **Provision the explicitly authorized operational branch.** Select operator, configuration, key custody and store. Establish how selected local results are proposed for repository admission.
6. **Complete real work and prove continuity.** Review selected outputs/evidence, persist an assessed lesson when supported, close the Agent session, restart and reconstruct the approved state for the next session.

The existing v2 suite took about 18 minutes with six isolated workers. That is suite duration, not measured transaction latency. Its passing receipt supports its exact candidate; any revised successor needs its own appropriate evidence before admission.

## Example of the destination

For a real task such as correcting an unresolved version reference:

1. A human selects the intent, scope and satisfaction check.
2. A fresh Agent receives a Context View bound to the selected State, plus an Ontology View of the relevant contracts, exact relations, history and gaps.
3. Its assignment and tool permissions bound the investigation. It produces a proposed correction and observed evidence.
4. A failed check can yield a classified Failure Occurrence, assessment and proposed Operational Lesson; it does not establish a general lesson by itself.
5. The human reviews the exact correction, evidence and supported lesson. The authorized transaction persists its selected effects and deterministic State/history consequences.
6. The session closes and short memory expires. A subsequent Agent reconstructs context from durable Project State and projections.
7. Later work records a Lesson Application and Outcome Assessment, so the Lab can distinguish stored advice from advice that helped.

## Guarantees preserved through every milestone

- Machine Agents remain ephemeral; durable continuity belongs to Project State. Session memory belongs only to its session and expires.
- Effective admission comes from exact Decisions/overlays, not source-body lifecycle labels or file presence.
- Global connections use declared Relation Kinds, typed axes, exact endpoint versions and closed qualifiers. Extensions are declared and reviewed. Ontology-local Edges retain their separate meaning.
- Semantic and governance histories remain independent. Context/Ontology Views, indexes and snapshots are rebuildable projections, not replay authority.
- Implementation admission, realization binding, adoption, execution permission, observed liveness, Product value and release are distinct effects/claims.
- Review the revised package and realistic example before admission. Bundle related effects where appropriate; do not ask for a second approval for deterministic bookkeeping.

## Scope and planning rule

This is a dependency roadmap, not a calendar commitment. Estimate each next bounded milestone after selecting its exact work scope.

Layer value = decision unlocked + user outcome + risk reduced.
Layer cost = implementation time + verification time + coordination burden.
Stop a layer when another addition contributes less value to its decision than moving to the next layer. Preserve earlier guarantees at every transition.

**Recommended next layer: L1.** The first next deliverable is the continuity design and a concrete successor plan; it is not another broad vocabulary expansion or a stable-release claim.
