Changing a governed system

The export investigation suggests three changes: revised code, an updated record format and different success criteria. They may share one review, but the reviewer needs to distinguish them. The code changes behavior. The format changes how information is stored. The criteria may change what completion means. CyberAlchemy Lab records each intended effect so an owner can see what is being accepted.

Lifecycle describes states and permitted changes through time. Different things have different lifecycles. The Lab can accept a record format while a particular record using it remains a draft. It can select software before activating it. A graph can actively represent a proposed source while preserving its proposed status. An agent session can end while the project continues. No single status answers all these questions.

The Lab names three distinct kinds of change. A Semantic Epoch is an owner-selected version of the accepted meaning: an owner-determined material change to the rule for which rows belong in an export requires a successor meaning version. A Representation Revision changes the designated machine encoding or format while preserving meaning, with explicit equivalence evidence, validation and owner selection. A Derived Refresh regenerates and validates a human-readable or lookup view from unchanged canonical input under an exact generator binding. It creates no new meaning, representation revision, decision or authority effect. Changing the generator follows its own tooling process. These distinctions prevent a formatting change from silently altering a rule.

A proposal identifies the things and versions concerned, exact file contents where relevant, requested effects, authority limits and conditions that would make it invalid. A Decision selects an outcome within those limits. A Decision Bundle presents distinct decisions at one checkpoint—a place where the person reviews them together. Each decision retains its owner, targets and permitted effects. Accepting one does not automatically accept the others.

An Admission Transaction applies an already authorized bundle. Admission means formal acceptance for a stated purpose and scope. The transaction checks the authorization, targets and input state, then applies the declared consequences together. These can include accepted records, receipts, history entries, updated Project State and generated indexes. Project State is the project’s saved records and knowledge outside any agent. The transaction adds no permission beyond the decisions it applies.

The inspected records show this arrangement in use. One governance approval covered record-type contracts, the Admission Transaction definition and connection-rule changes. Their consequences were applied together. A later approval accepted the local runtime implementation—the software performing selected Lab operations—and its declared operational records. Each approval identifies its scope. Deployment and publication have their own authorization requirements.

Two histories retain separate accounts of the result. Project Semantic Event History records complete resulting project states and their predecessors: what changed. Project Governance Event History records the decisions, authorization, policies, challenge rules and evidence for those particular changes: why they were accepted. Both identify the same specific change events so a reader can join the accounts without confusing their roles.

Event sourcing is the engineering idea of retaining an ordered change history and reconstructing state from it. Replay performs that reconstruction from recorded inputs. The Lab adds a separately linked history of authority. Reconstructing a state does not itself decide whether its inputs were accepted under the applicable rules. [Martin Fowler, Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html).

The local implementation demonstrates a limited form of this mechanism. A signed proposal identifies the intended changes and expected starting state. An exclusive writer lock prevents competing local writes; prepared transaction records are retained before the reference to accepted state is updated. Recovery distinguishes completed history from recognized unfinished work. The recorded evidence concerns interruption of a local process on the selected filesystem. It does not establish durability after power loss or coordination across machines.

A Challenge Contract specifies who may contest a revision, acceptable reasons and evidence, who responds, timing and resolution requirements. A Challenge Event records a particular eligible challenge. For example, missing-row evidence can challenge an export-completeness finding. Filing it creates a matter that the contract requires someone to resolve. Suspension, withdrawal or a changed meaning still requires the applicable rule and an authorized decision.

After an accepted change, the next agent may need different information. A Context View is information selected for a task, with source versions and conditions for its use identified. A view prepared before the change can become stale. The runtime can require a new selection tied to the accepted state before work continues. The agent recovers the change and its authority from project records rather than relying on a remembered conversation.
