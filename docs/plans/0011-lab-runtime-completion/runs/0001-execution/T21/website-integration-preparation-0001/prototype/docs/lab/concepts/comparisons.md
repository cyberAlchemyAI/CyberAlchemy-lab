<a id="meaning-and-record"></a>

## Meaning, format and the particular record

Meaning, record format and a particular instance answer different questions. Keeping them identifiable lets formats evolve under their own version rules while preserving the governing meaning.

**[Definition](../reference/records/def-cal-definition-definition.md#def-cal-definition-definition) What does it mean?**

“Complete export” states the identifier-coverage criterion and its scope. An accepted exact version governs that meaning.

**[Artifact Type](../reference/records/def-cal-definition-artifact-type.md#def-cal-definition-artifact-type) What must this kind of record contain?**

The Work contract binds meanings, canonical structure, validation and representation requirements for Work records.

**[Artifact](../reference/records/def-cal-definition-artifact.md#def-cal-definition-artifact) Which particular recorded item?**

This investigation’s Work record has its own identity, version, owner and state, under its declared type.

A valid structure can still await definition acceptance. An accepted type leaves each instance to its own standing. A new display leaves the underlying meaning unchanged.

<a id="purpose-and-effort"></a>

## Need, promised value and bounded effort

**[Intent](../reference/records/def-cal-definition-intent.md#def-cal-definition-intent) What need matters?**

Customers need complete eligible data. Intent Resolution selects a response and the conditions for judging satisfaction.

**[Product](../reference/records/def-cal-definition-product.md#def-cal-definition-product) What enduring value is promised?**

The customer-data platform provides export capabilities. Its capability is the promised outcome; a particular Implementation realizes it.

**[Project](../reference/records/def-cav2-d60.md#def-cav2-d60) What coordinates the effort over time?**

The export-repair Project keeps its goals, decisions, evidence and work together.

**[Goal](../reference/records/def-cav2-d59.md#def-cav2-d59) What future result must be established?**

A scoped repair outcome, with achievement criteria, required evidence and an accountable owner.

**[Work](../reference/records/def-cal-definition-work.md#def-cal-definition-work) What is the bounded effort?**

Investigate Northstar’s output using selected inputs, constraints and expected results. Work can also exist outside a Project where its contract permits.

Finishing investigation supplies a Work result. Product delivery and repair-goal achievement need their own criteria, evidence and transitions.

## Observation, evidence and assessment

**[Operational Observation](../reference/records/def-cal-definition-operational-observation.md#def-cal-definition-operational-observation) What was observed?**

The comparison records 200 missing required identifiers in E12. In ordinary Project work, this is an Operational Observation; research- or experiment-specific Observation has its own boundary.

**[Evidence](../reference/records/def-cal-definition-evidence.md#def-cal-definition-evidence) What bears on a particular claim?**

The source snapshot, output and comparison support the scoped omission claim when their provenance, method and suitability can be examined. An Evidence Set groups the relevant material.

**[Failure Assessment](../reference/records/def-cal-definition-failure-assessment.md#def-cal-definition-failure-assessment) What conclusion is supported?**

The occurrence is established in this output. Cause, wider impact and recovery remain unresolved and are evaluated independently.

An observation supports particular claims under conditions. The omission leaves pagination cause and repair to be established. A Decision chooses a response under the applicable authority.

<a id="assignment-and-permission"></a>

## Assignment and permission

**[Agent Assignment](../reference/records/def-cal-definition-agent-assignment.md#def-cal-definition-agent-assignment) Which participant has which job?**

Assign the agent to investigate the omission as a Work item.

**[Delegation](../reference/records/def-cal-definition-delegation.md#def-cal-definition-delegation) Which actions are permitted, and when?**

Permit inspection, comparison and preparing candidate material within a recorded scope and time window.

**[Definition authority](../reference/records/def-cal-definition-authority.md#def-cal-definition-authority) What criterion governs this meaning?**

The accepted completeness definition governs the identifier-coverage assessment within its declared scope.

The agent needs assignment and current permission. Knowing completeness’s meaning supplies no automatic data access, deployment or closure authority.

<a id="state-and-views"></a>

## Saved state, selected views and session memory

**[Project State](../reference/records/def-cal-definition-project-state.md#def-cal-definition-project-state) What endures?**

Governed external records, definitions, decisions, evidence, relationships and histories—including preserved proposals with their own standing.

**[Context View](../reference/records/def-cal-definition-context-view.md#def-cal-definition-context-view) What information answers this task request?**

An immutable selection bound to the request, exact sources and declared usability conditions.

**[Ontology View](../reference/records/def-cal-definition-ontology-view.md#def-cal-definition-ontology-view) What connected model is selected for this purpose?**

An immutable projection of an exact consistent ontology cut, with purpose, consumer, freshness, expiry and limits.

**[Session Memory](../reference/records/def-cal-definition-session-memory.md#def-cal-definition-session-memory) What is temporary working memory?**

Working memory belonging to one Agent Session. It expires when the session terminates.

Views select saved state while preserving its canonical sources. A new machine session uses a new instance, working memory, checked views and applicable permission.

<a id="ontology-and-craft"></a>

## Lab ontology and the Craft software model

| Question | Lab ontology | Craft software model |
| --- | --- | --- |
| What is represented? | Typed project subjects and declared connections, with meanings, evidence, ownership and governance. | Software responsibilities, behavior, architecture and construction constraints. |
| What does the incident use it for? | Recover how the investigation, inputs, assessment and decisions fit together. | Express and construct the proposed software repair within supported model-to-code paths. |
| What does a graph connection establish? | Only the meaning allowed by its declared ordered endpoints and qualifiers. | The software relationship defined by Craft’s applicable model contract. |
| What requires a separate decision? | Acceptance and permitted effects on governed Lab state. | Adoption of outputs and any release or deployment through the applicable authority route. |

Craft contributes software-design tools within the Lab. Models, code and checks can enter Work as outputs and evidence. Their explanatory fit supplies no automatic operational connector.

A graph node represents a governed subject. Its appearance supplies no new authority, and a Craft edge does not automatically become a permitted Lab instance relation.

<a id="calculation-and-operation"></a>

## Calculation, Query, Rule and Operation

**Rule Does a condition hold?**

Evaluates a Boolean condition.

**Calculation What value follows from the inputs?**

Derives a value without changing business state. In the capacity fixture, it returns Accept or Reject.

**Query What information is retrieved?**

Retrieves the selected information under its declared contract.

**Operation What business state change is requested?**

Owns the state-changing behavior, such as reserving capacity. A rejected attempt can leave state unchanged.

| Request / capacity | Calculation result | Supplied capacity afterward |
| --- | --- | --- |
| 4 / 5 | Accept | 5 |
| 5 / 5 | Reject | 5 |
| 6 / 5 | Reject | 5 |

Accept is a calculated value. Reservation needs a separate Operation and permitted state change. Numeric Calculations also remain derived values.
