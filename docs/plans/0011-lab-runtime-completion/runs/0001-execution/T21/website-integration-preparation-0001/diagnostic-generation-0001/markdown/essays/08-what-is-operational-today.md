## What is operational today

To understand the Lab’s current state, we need to distinguish the model, accepted contracts, implementation and observed executions. This essay retains the snapshot inspected on 8 October 2026. It includes accepted Project State and acceptance of a local runtime. Product and release work is still ahead.

The snapshot selects 183 definition identities from 189 accepted versions, and 121 record-type contract bindings from 143 accepted contract records. It also selects 41 relation kinds, 109 endpoint kinds and 550 permitted ordered pairs. Bindings identify applicable contracts or schema sections. These totals count catalog entries, without measuring installed features or coverage of project files.

The descriptor count is different: 114 selected accepted descriptors, plus seven bindings selecting shared foundation-schema sections, yield 121 bindings. Separately, seven unaccepted descriptors concern earlier contracts. Historical and duplicate-resolution records are retained too. The two sets of seven answer different questions, so the total is not a readiness score.

Earlier approvals established the operational foundation, initial Project State, agent-context example and transaction contracts. On 7 October 2026, another approval accepted the local runtime and specified consequences. Its bundle has 17 generated records, including updated Project State and six typed connections. Both histories identify the transition. The current-state reference locates the bundle while history supplies reconstruction.

The admitted implementation offers local commands on demand for inspection, governance queries, task preparation, authorized record changes, reconstruction and bounded recovery. Its admission excludes a general organizational-permission evaluator, continuous service, external deployment and production durability. That acceptance records no activation or external effect.

The runtime uses a fixed earlier source selection. Later acceptance does not update it automatically. A proposed successor selects later state while retaining the earlier implementation. Its review records 38 passing checks and an isolated work-and-context demonstration. Those results support the proposal, whose acceptance is still separate. This editorial pass reruns none of those implementation checks.

A returning agent needs the accepted-state identity behind its context and an account of newer records. The fixed selection makes that boundary visible. The proposed update addresses later-state selection. Keeping runtime selections and task information aligned remains part of repeatable-operation work.

Ontology evidence has its own scope. The records include acceptance of an implementation binding, adoption of a Rust lifecycle library and an authorized past local execution. A migration prototype has bounded product approval. Its manifest lists 21 packages, 815 nodes, 1,210 relationships and 422 documents. Imports retain source qualifications and supply no blanket acceptance or coverage of current objects.

The lifecycle library loads events, reconstructs consistent cuts, joins governance records and produces views. The graphs are calculated outputs. Some overviews retain earlier proposed wording; subsequent acceptance and adoption establish effective standing. Adoption, past execution, current operation and consumer cutover need separate evidence.

The roadmap proposes foundation, repeatable operation, integrated work, a scoped coherent ontology and a usable product. These add continuity, refreshed agent information, engineering and research connections, failure assessment, lesson use, installation, recovery and upgrades. Planning the stages leaves their completion to evidence.

The intended loop starts with a need and response, then current information and permission for assigned work. Results are assessed, owners review proposed changes, and authorized consequences enter Project State with separate change and approval histories. Updated views prepare the next session. Failures and feedback can also produce lessons whose use and benefit are assessed.

A useful next demonstration would take a real Work item through that loop under an authorized runtime selection, accept another change and prepare a fresh session. It should show continuity, recovery and handling of evidence or unresolved work. The repeatable-operation stage proposes it. Permanent provisioning and activation still need operational authorization.

A stable release has yet to be established. Architecture, source-authority rules, publication review, repeatable evidence and approval of exact release bytes are prerequisites. The Lab has an accepted local foundation with unfinished work alongside it. Explicit records let the next participant recover those facts and contribute results another session can examine.
