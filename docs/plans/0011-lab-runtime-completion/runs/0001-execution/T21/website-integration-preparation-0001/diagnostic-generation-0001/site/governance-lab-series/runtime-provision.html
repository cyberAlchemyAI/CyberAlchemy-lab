Provision a branch and review its authority

Separate environment selection, store creation, key custody and approval.

Draft prepared on 2026-10-14. Integration and final T21 qualification remain pending.

Choose the kind of provisioning

Local v1 init creates a new operational branch. Candidate provisioning constructs a separately scoped branch from pinned runtime/configuration/baseline/HEAD. Composite operator preparation additionally selects three independent branch workspaces, policies and authentication proofs. These actions are not interchangeable.

Read CandidateScope and CandidateBranch for controlled branch construction, bootstrap composition for seed packaging, and v1 admission for its local scope. A package, key, store and admitted implementation each answer a different question.

Check the environment before the branch

Select the exact executable, parser, profile, dependency closure and supported filesystem assumptions. T07's 1010-file selected dependency declaration identifies installation0004; its existence is not a new-install witness or a blanket compatibility result for every package.

Confirm the source cut and current byte checks before selecting a new store. A historical profile may be useful for inspection while lacking current records. Installing Python/native dependencies does not initialize a branch, provision authority or activate a service. The CLI/environment reference keeps those interfaces separate.

Keep credential custody explicit

A local approver key remains outside Git and outside public artifacts. A reader policy selects a bounded Principal, source, scope, operations, budgets, expiry and nonce channel. Private signing bytes, credential paths with real secrets and live private policy bodies do not belong in task text, replies, exports or tutorial logs.

For the composite candidate, Base, Action and Governance need independent current branch selectors and three proofs. The operator contract explicitly selects the outer policy custody root separately from Base's actual nested Vault and its original workspace/workspace.json. Copying an outer manifest cannot stand in for the real Vault.

Review before authorizing

StageWhat it establishes
Environment/source inspectionThe selected inputs are available and match declared bytes
Branch initializationA new scoped store/configuration exists
Candidate reviewConsequences, contracts, source cut and unresolved obligations are visible
Exact signed authorizationThis local approver approved these bytes within this boundary
Application and cold replayThe observed scoped effect and its committed chain
Repository admission or service activationSeparate governing and operational evidence

Review failures stay attached to their exact input version. A technical provisioning receipt cannot become Action/Governance or genuine owner authority merely by being passed to another component.

When provisioning refuses

An existing path, changed baseline/HEAD, unsafe root, missing public key, expired/revoked policy or unknown execution origin should refuse. Preserve the actual error and owned partial state. Choose a separately authorized new branch or correct a new candidate version; do not silently overwrite, restore old Session RAM or extend a historical period.

Fresh setup and full three-branch operation remain pending for the changed API17 composition. Follow status and recovery before interpreting a refusal as a reason to rerun.
