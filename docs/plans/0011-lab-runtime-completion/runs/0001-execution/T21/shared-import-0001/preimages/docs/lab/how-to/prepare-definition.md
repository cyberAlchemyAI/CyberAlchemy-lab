# Prepare a definition for review

State an exact meaning and prepare its review obligations without assuming acceptance.

<a id="definition-result"></a>

## Result and prerequisites

The owner needs an exact candidate meaning and its review material. Select the Definition contract, semantic owner, scope, sources, consumers, registry/index route and drift route. The [complete criterion specimen](../reference/record-examples.md#example-definition) uses Definition/v2.

That specimen passes the selected schema while source posture and acceptance obligations remain open. It helps examine structure. Real source and owner evidence still have to be prepared.

<a id="definition-meaning"></a>

## 1. State the meaning and its boundary

Name the term, stable identity and proposed version. State the governing meaning with applicability, exclusions and boundaries. For identifier coverage, declare S, A, F and E, requiring every RequiredIds(S,A,F) identifier in ExportedIds(E).

Value accuracy, live-source consistency, access permission and recovery are outside this criterion. An export with all IDs and incorrect values exposes that boundary while still satisfying identifier coverage.

<a id="definition-voices"></a>

## 2. Align the three voices

The scientific/formal voice governs meaning. Plain-language and domain-context voices explain it without expanding its scope. “Every customer record everywhere” would be a different claim from one fixed account, filters and snapshot.

Make conditions and notation testable. Keep a satisfying example and a failing example with their selected inputs visible to the reviewer.

<a id="definition-review-material"></a>

## 3. Prepare the review obligations

1. Bind source identities, selectors, digests and admitted source posture using the applicable source contract.
2. Identify primary consumers and any affected meanings, formats or connections.
3. Prepare the registry postimage (the proposed registry contents after the change) and synchronized index entry; preserve the exact canonical JSON and generated projection relationship.
4. Declare the current drift audit, accountable owner and challenge route.
5. Inspect internal consistency and non-collapse: meaning must remain separate from representation, classification, permission and lifecycle standing.

A schema pass covers representation. Reference closure, source posture, generated-view consistency, registry/index and semantic review still need separate checks.

<a id="definition-output"></a>

## Expected output and owner decision

Submit the exact version, formal meaning, explanations, boundaries, source evidence, affected consumers, proposed registry/index changes and findings. Keep open obligations visible. Authority for that version and scope comes only from the applicable exact owner decision.

Review for acceptance inferred from structure, changed meaning disguised as formatting, explanations exceeding formal scope, and agent permission inferred from definition acceptance.

A changed meaning follows its semantic route. Accepted changes also need affected consumers and derived views updated under their own rules. The [lifecycle distinctions](../guide/lifecycle.md#change) explain those routes.
