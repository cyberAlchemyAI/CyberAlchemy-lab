# Unselected external witness adoption contract

The selected O06 proof is conditional on putting the actual accepting Decision hash into the event provenance before deriving the unsigned target core. The permissive original `ProvenanceEntry.source_ref` field does not establish a universal impossibility. No currently selected rule authorizes this proposed replacement convention.

A real candidate convention would use an independently selected stable authorization-intent identifier in the native event provenance. A trusted materializer would construct the complete event from grounded representation and current scope, seal it with the original Rust algorithm, and fix the exact event bytes/native seal digest, schema/materializer/source identities, semantic tuple, complete resulting state, role/assignment, expected per-stream version/head, operation/core identity, and exact ordered batch. An owner would then review those fully known effects through a selected authenticated route. The positive response would sign an independently fixed challenge binding that complete batch, exact unsigned cores, principal, assignment/scope/source, nonce, and bounded period. The actual Decision would be generated from that verified response and exact effects using the selected original Decision rules. An external witness would bind the exact response and Decision bytes to the fixed event/core commitments and stable provenance identifier.

The native event must remain byte-identical after the response and Decision exist. The event's stable identifier would resolve to the exact external witness under the new explicit consumer rule; neither an arbitrary `source_ref` nor a caller-provided witness locator suffices. The consumer would require protected independently pinned issuer/rule/configuration inputs, full byte capture and source/schema/role guards, fresh currentness and per-stream-head checks, exact positive response and Decision validation, exact target/core correspondence, original append-only history and predecessor checks, and a locked pre-effect gate. Unknown or changed authority, heads, mappings, or witness bodies would refuse. Retry/recovery would preserve original exact receipt inspection and indeterminate-outcome handling rather than replaying a response as a permission.

This executable prototype implements the pure binding direction with new external fixture domains. It deliberately stops short of native sealing, original D01 unsigned-core generation, original operation recovery, persistent replay reservation, authenticated human ingress, and native append. Actual adoption is always refused. No fixture head/version, source currentness flag, signing key, role assignment, or synthetic Decision can satisfy those missing prerequisites.

The alternative with two checkpoints requires a known first materialization-permission Decision before the event is fixed. The second actual adoption Decision then accepts the fully known event externally. Putting the second accepting Decision's digest back inside that same event restores `Decision bytes -> Decision digest -> event bytes -> target digest -> unsigned core -> Decision bytes`. Adopting either alternative therefore requires a reviewed explicit change to the selected provenance/adoption convention; the original schema's permissiveness is not that selection.

The original 88 rows are inherited by exact account pin and remain individually blocked. This proposal changes none of their event bytes, event digests, unsigned cores, Decisions, owner responses, dependency flags, exclusions, or role/axis bindings. The broader 363-target package and 36-task/73-edge plan remain outside this component's completion claim.
