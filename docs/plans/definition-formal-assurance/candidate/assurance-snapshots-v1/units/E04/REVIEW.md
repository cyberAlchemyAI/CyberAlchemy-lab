# E04: adversarial checks of the formalization boundary

This unit assembles an explicit denominator of 76 existing, source-bound adversarial fixture methods across eight formalization aspects. The selected fixtures execute real parser, type, relation, search, independent witness, publication and record-replay paths. E04 adds a closed registry, checks that its cases cannot be omitted or redirected, and runs every declared fixture without accepting skipped tests. The mandated command passed in run-001: all 76 fixture methods passed, with no skips, errors or failures. The three enclosing E04 tests passed in 187.741 seconds. The command and complete per-case results are retained in the numbered attempt. The 506 prior sealed files stayed unchanged.

The full episode still covers 183 current definitions and 189 admitted source versions. Seven governance definitions have partial candidate interpretations, with owner fidelity pending. The existing eleven checked existential results remain conditional on selected types, assumptions, carriers and exact bytes. This unit contributes safeguards for handling those interpretations and future definitions. It supplies no additional whole-definition translations or proofs.

## How the controls are grounded

The registry stores each case identity, category, fixture module/class/method, exact source-file SHA-256, method SHA-256, source line, complete fixture assertion contract and selected expected diagnostic or status literals. Several fixtures assert structural or numerical facts rather than a named diagnostic; their full assertions remain present and byte-bound. The literals are an indexing aid. A literal's presence alone is not evidence that the checked outcome occurred: the actual fixture must run and all of its assertions must pass.

The controls deliberately reuse established isolated fixtures. These fixtures have already encoded important failure conditions, including race callbacks and independently selected inputs. Reusing them preserves their exact mathematical and operational expectations while creating one explicit cross-layer denominator. E04 does not claim to have invented 76 new fixture implementations. The new registry checks test omission, duplication, unknown fields, rerouting, missing methods, stale source binding, invented causes, forged readiness, boolean counts and duplicate JSON keys. These checks protect this suite's own execution contract.

The suite validates the registry before importing fixture routes. Routes are restricted to selected existing test classes. Each selected case runs through a `unittest.TestSuite`, which supplies both instance and class setup/cleanup. The execution result must show one run, zero skips, zero errors, zero failures, zero expected failures and zero unexpected successes. An expected failure cannot be counted as a successful hostile control. Registry order and all 76 identities must match the execution report exactly.

Source-code and canonical-source mutation are excluded from these fixtures. Hostile changes occur in copied or temporary fixtures and in-memory candidate values. The 506 files sealed by A10 are rehashed before and after execution. The finalizer also rechecks the captured sources and upstream bindings before recording delivery. The suite's new files stay in the declared E04 candidate write scope. Older receipts and source-owner review packets remain byte-preserved.

## What the passing suite establishes

Passing means that the declared fixtures reached and satisfied their actual assertions with the current selected implementation and runtime. Positive controls matter because a checker that rejects every input would fail them. Negative controls matter because serialization, typing, truth checking, scope checking and evidence accounting are different safeguards; success in one cannot replace another. A valid model with a forged provenance binding should still fail. A well-formed request with a missing population denominator should still remain unresolved or be rejected. An interrupted search should preserve uncertainty even after it has checked some models.

The retained results identify executed fixture methods and their aggregate outcomes. They do not serialize every underlying provider response or every nested subcase. The complete byte-bound assertions specify what each method checks, and the retained output shows whether those assertions passed. The case count therefore denotes fixture methods, not all individual mutations, mathematical interpretations or source clauses. The three enclosing E04 tests and the registry's mutation subcases have separate counts.

## Limits and remaining work

These controls are a finite selected adversarial set, not exhaustive fuzzing and not a proof that all malformed inputs are contained. They do not establish soundness of Python, JSON Schema, the operating system, the shared type/compiler code, the dependency generator or the independent reference itself. Existing trust boundaries remain explicit. The real no-replace controls depend on the currently supported Linux operation. Simulated unavailable-operation and race conditions exercise the declared failure paths; they do not establish behavior on every platform or under every possible crash.

The suite checks that witnesses, bounded searches and pending gates retain their distinct strengths. It supplies no independent generic exhaustion checker, kernel theorem proof, source-owner decision, real grant legitimacy, semantic admission or complete semantic dependency closure. The exact A10 owner review remains pending. All earlier whole-clause omissions and source precedence questions remain unresolved.

After verified E04 delivery, I01 can add transitive invalidation for revised source and dependency inputs. Subsequent I02–I05 work covers obligation regeneration, selected-snapshot regression, the candidate CLI and revision rehearsal. The L1 workflow exit gate still precedes the wider family translations and the full episode review. Completion of these 76 controls cannot close that gate or the overall goal by itself.
