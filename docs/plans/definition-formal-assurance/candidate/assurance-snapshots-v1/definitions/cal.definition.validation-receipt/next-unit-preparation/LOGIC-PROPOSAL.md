# Artifact: proposed definitions, types and logic

This design selects cal.definition.artifact@1.0.0-candidate.1 at SHA-256 554dda3aec8fb66fdfd2a910d90defa56235705e482fa24184f31957a2b1d785. C53 admits the current Definition meaning. Its retained reconstruction body and CAV2-D51 source posture remain historical inputs; that admission does not accept this translation or authorize any instance. The native Artifact interpretation and models must wait for Receipt's full seal and separate successful delivery audit.

The genus is an identity-bearing, typed, versioned record produced or maintained for a declared purpose. Explicit machine representation, generated human projection, ownership, provenance, lifecycle posture and validation surface distinguish it from an ungoverned working note. Canonical Artifact is a qualification of an instance. It is distinct from the canonical-kind enumeration and from an authoritative source version. A process-origin declaration identifies an allowed producer and process; it does not establish observed execution.

Start with separate descriptive sorts Artifact, ArtifactIdentity, ArtifactTypeReference, ArtifactVersion, PurposeReference, MachineRepresentationReference, HumanProjectionReference, OwnerReference, ProvenanceReference, LifecyclePosture, ValidationSurfaceReference and Context. Keep CanonicalKind, AuthorityKind and Durability separate, with an explicit embedding of admitted authority kinds into canonical kinds if the owner accepts that map. Never identify their carriers or infer that every canonical kind bears authority. Keep ProducerReference, ProcessReference, ProcessVersionReference, OriginStatementReference, OriginAssurance, IntegrityReceiptReference, ActorReference, IdentityPolicyReference, ExternalSignatureReference and Digest separate. These names are mathematical carriers and do not create absent canonical Definition identities.

Artifact scalar projections are total on their descriptive carriers. Selected records require exact nonempty declared references and one scalar canonical-kind and process-origin tuple. The allowed-origin relation is set-valued over kind, producer, process and process version; more than one allowed producer can exist for a kind. The artifact selects one exact tuple from that relation. A current owner-approved allowed set is a separate declaration and review obligation. A candidate-only producer or unresolved reference must not satisfy the selected origin guard.

Authority-kind and durability projections must agree with the selected kind's derived projections. They cannot be independently chosen by an instance. The mapping is explicit, with unresolved kind table and reference denotations recorded as residue. Do not import an unavailable canonical-kind Definition, silently resolve semantic.artifact-lifetime as a concrete consumer, or merge Artifact with the canonical-representation-invariant sibling because they share D51 lineage.

Use three distinct OriginAssurance constants DECLARED, INTEGRITY_BOUND and ACTOR_ATTESTED. An exact assurance tag must lie in this declared vocabulary. DECLARED requires the exact owner/source origin statement. INTEGRITY_BOUND additionally requires a declared verifier receipt binding the exact statement and artifact-state digest. ACTOR_ATTESTED additionally requires separately sorted actor, policy and external-signature references bound to the exact tuple. The source identifies actor-attested as a future level rather than a currently available result. A shape-valid signature reference is not a verified external signature or identity-policy result; leave actual mechanism satisfaction and present operational availability separately unresolved.

A proposed scoped CanonicalDeclared predicate is equivalent to declared canonical-kind membership, declared owner admission of the exact origin, an exact tuple in the current owner-approved allowed set, and a recognized assurance tag with its necessary declared support bindings. This is a proposed interpretation of the source biconditional. Its declared admission and approved-set predicates must remain visibly qualified until an owner accepts their actual denotations. It must not turn the biconditional into automatic governance admission. Outside-scope instances remain unconstrained by these selected guards.

Actual process execution, origin truth, integrity verification, actor authentication, signature verification, artifact correctness, validation, trust, discharge, authoritative status, promotion, adoption, publication, deployment and external effect are separate targets. Neither canonical declaration nor any assurance tag assumes those targets. Countermodels should keep the typed declarations and required witnesses true while each actual target is false. Independently supported actual outcomes must also be permitted, so non-entailment cannot become denial.

Required witnesses should include a selected ordinary Artifact, a selected declared canonical Artifact, a kind with more than one allowed tuple, two instances selecting different allowed tuples, independently supported actual authority without collapsing canonical qualification, a canonical declaration without actual authority, the integrity-bound declared-support branch without actual verifier success, the future actor-attested declared-support branch without an actual signature result, and an outside-scope record. Actual population availability, empty enumeration policy, admission identity and operational assurance levels remain owner review decisions.

Negative controls should alter scalar reference sorts, omit selected identity/type/version/purpose/ownership/provenance/lifecycle/validation references, choose an undeclared or candidate-only producer, change process version, bind a tuple allowed only for another kind, choose authority-kind or durability values that disagree with kind-derived fields, omit exact statement/digest support, collapse assurance tags, merge sibling identities, infer execution from process-born wording, and infer authority or publication from canonical qualification. Also reject signature arity, non-total functions and ill-sorted function results. No theorem or empirical assurance follows from a finite control count.

Exact source accounting must retain all normative, boundary and scope text. The four source testable conditions concern Definition identity, source digest currency, Definition/v1 shape and generated projection. Their successful local checks do not discharge process-origin, allowed-kind, assurance or authority semantics. Keep these representation observations separate from encoded semantic clauses. Keep plain-language and domain-context intuition explanatory; retain incompatible historical postures as explicit owner findings.

The next DAG starts with the exact source inspection, follows type/signature design and accepted source correspondence, then finite populations and controls, countermodels, fresh native checks, frozen typed evidence and a separate audit. Current carrier and consumer observations, reachable dependencies and inventory precede the later full review and delivery seal. Source fidelity, whole proof and owner acceptance remain pending throughout this source-only proposal.
