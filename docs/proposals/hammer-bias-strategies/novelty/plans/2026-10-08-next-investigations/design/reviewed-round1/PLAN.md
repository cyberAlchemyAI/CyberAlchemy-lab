# Investigate novelty by changing what can be proposed

A clever explanation does not yet escape the hammer. The next investigation should produce an **operation we can perform or an observation that separates rival explanations**, then show exactly where it differs from ordinary analysis and a generic creativity prompt.

The working unit is one **operation–rival–defeat card**: valued outcome; assumed necessary tool/action; changed dependency or operation; rival account; opposing predictions; smallest discriminating probe; what would defeat it; resource/uncertainty disposition; raw source ID. “No viable opening” is an admissible result. This unit is small enough to compare and complete enough to retain through Distill and selection.

Start with [portfolio.json](portfolio.json), which contains every arm, metric, dependency, failure rule and budget. [BASELINE.md](BASELINE.md) binds the preceding results; [SOURCES.json](SOURCES.json) records exact source hashes. The predecessor run stays unchanged. This is a plan; none of these new comparisons have run.

## What counts as progress

Keep five outcomes separate: **creation → feasible discrimination → preservation → exposure → decision/world value**. Credit local causal-operation or question families against the frozen archive and both concurrent controls. New wording, an equivalent contrapositive, a longer disagreement and summary-only invention receive no creation credit. A valid proposed test is not a measured physical effect. A changed second slot is not improved human judgment.

The earlier run motivates this separation: backcasting produced one exclusive qualified raw proposal whose complete test retention remained uncertain; compression introduced seven unsupported extensions versus zero ordinary; deferred convergence had no consistent qualified-probe advantage; alternative slots changed historical exposure, while fresh pools offered no eligible replacements. These findings justify targeted comparisons and possible negative conclusions, not automatic adoption.

## Preparing a fair comparison

Before scores, freeze outcome, supplied observations, hard constraints, resource inventory, ordinary-family archive, prompt versions, opaque arm mapping, maximum openings, assessed object, fit categories, protected fields, role schedule and review boundaries. Generators see evidence/constraints but no archive answers or method examples. The independent archive author does not see candidate outputs. Equal evidence and saved-text allowances apply within each comparison; count extra stages and actual burden explicitly.

Primary generation pilots use two fresh matched blocks: one hammer-like design problem and one analysis-workflow problem. Confirmation uses four untouched blocks, two per domain. Old library/kit outputs are development diagnostics only. I09 separates its two known diagnostic packets from four untouched pilot packets, then four fresh confirmation packets. I01 is a launch-readiness calibration, not a study proving calibration improvement. Two pilot and four confirmation blocks cannot establish broad generalization or statistical power. Cross-study reuse preserves pairing but creates no independent replication.

For the hammer case, preserve “secure joint” while challenging whether impact is necessary. Then separately test a return arrow: does a hammer-oriented joint specification create future demand for impact? Compare return-link removal against a sham while initial demand is held equal. The contrapositive alone changes no mechanism. For attack-to-construction, attack a dependency and require a replacement, removal, test or explicit no-opening. For conversion/carrier, test whether a disturbance itself creates a usable signal, including false signals and cancellation, and account for any work displaced onto a person. For interfaces, preserve each parent while breaking only the link and specify an observation that should change.

Each raw opening receives two blinded independent judgments. Save raw assessments before compression; score retention separately after compression. Preserve every raw ID as retained/merged/parked/rejected, including uncertainty and all defeat conditions. New ideas must live in a separate proposal field and receive no preservation credit. Adjudication is scalar-only and bounded; unresolved causal-family disagreement remains uncertain rather than forced agreement.

Reviewer packets share immutable sources by hash while preserving unit, contrast and lineage coverage. Reuse judgments only if source, rubric, archive, assessed object and context hashes all match; compression output changes require fresh dual retention review. I09/I13 shards contain at most three complete case packets. Check capacity on unscored fixtures before freeze; if it does not fit, rebudget and re-freeze. Saved words are burden proxies, not token measurements.

Record planned, attempted, valid, evaluable, gated, no-opening and qualified denominators; raw creation, complete-retention conjunction, unsupported additions, eligible exposure and displacement. Report rates plus underlying counts, both domain strata, costs and missing evidence. A protocol-invalid case stays in the planned denominator with its reason; an unresolved fit is not an explicit hard-constraint relaxation.

## Robot Talks, human choices and physical evidence

I08 and I12 test **convergence within a fixed concern architecture**. They do not estimate the complete Robot Talks skill or the two-lane architecture. A whole-skill benefit would require a separate frozen full-workflow-versus-equal-budget control and its own resource/schedule contract; its budget is intentionally unspecified until that workflow is selected. The installed skill's concern-report and human-validation stages must remain visible.

The optional I10 human pilot is eight participants × four distinct cases (32 decisions), one generation×view cell per participant per case. Balance all four cells twice per case and counterbalance order. Confirmation uses16 new participants and four new cases (64 decisions), with new upstream pools separately charged. Treat participant as the clustered unit and case as a block. Freeze task payoff/oracle before choices; a synthetic task result supports only that task. Prospective screening gate: positive mean task-value difference, no increase in constraint violations and median decision time increase≤20%; show uncertainty. This practical threshold is a planning choice, not validated prior evidence.

No equipment, participants, operating data or recruitment authority is assumed. Physical followups require exact materials, load directions, force/slip measurements, sham/comparator, observation time and feasibility evidence before declaring a test informative. Budget and schedule them separately before launch.

## Failure handling and completion

Missing source bindings, incorrect arm attribution, absent lineage or unsupported fit categories block scored launch. Preserve evidence for the block and allow separately logged repair; never overwrite first saves or historical results. Incomplete native work remains timed-out/blocked/handed-off with residue, not completed because an output file exists. Typed events include phase, event kind, study/block/arm/unit IDs, native handle, turn, prompt/source/output hashes, dependencies, terminal witness and repair_of. Progress, design/audit joins and experimental joins occupy explicit distinct partitions.

A wave closes with complete schedule-to-terminal coverage, gate dispositions, blinded mappings, immutable first saves, raw-to-summary-to-view lineage, budgets and an independent completion audit. [future.dispatch.json](future.dispatch.json) describes the route. Its validator checks structure/governance; it grants no execution admission or effectiveness claim. Future launch uses the user instruction and resource scope then in force, without asking again for already-authorized actions.

The smallest extension is an added resource-bound probe or a genuinely new operation–rival–defeat card. Revisit this plan when constraints, available observations, archive families, compressor instructions, case population or execution runtime change. Keep the five outcome levels separate when extending it.
