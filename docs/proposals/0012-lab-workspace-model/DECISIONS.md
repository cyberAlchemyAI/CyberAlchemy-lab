# Candidate design decisions

These are authored selections for this proposal, not owner admission Decisions.

1. **Use a scoped Lab Workspace meaning.** One workspace has one primary Project in this profile, an optional Product or another declared purpose, selected canonical-home references and an exact parent-model binding. Project, Product and workspace identities remain separate. A Goal, Person, Team or Work record does not automatically become another workspace.
2. **Keep runtime installation separate.** The explicit user answer during the corrective Define pass selects Lab Workspace for the durable modeled scope and runtime instance for execution. The answer is recorded in the successor Pack. It does not establish general acceptance of the full Workspace Definition or native authority. The unqualified phrase Lab instance is not a canonical alias in this candidate.
3. **Use existing current carriers.** The live selected registry supplies Definition/v2, Governed Model/v1, Model Instance Binding/v1, Canonical Package Manifest/v1, Project Identity/v1 and Goal/v1. Generic Project/v1 is a resolved duplicate. Definition/v1 is historical. No new global workspace Artifact Type is registered.
4. **Keep JSON primary inside the candidate.** Definition Markdown uses the existing bound v2 generator. Package Markdown is generated by this candidate's renderer. The candidate-only Definition index never updates the live registry.
5. **Select Craft without overwriting representations.** `craft/project/project.json` is the profile's primary Project input after byte-equality comparison with the coordination copy. `craft/product/product.json` is its selected v2 Product proposal; the previous v1 representation retains its own standing and exact bytes. This creates no admission or automatic supersession.
6. **Preserve Goal membership posture.** Foundation Goal selection retains its existing-source-reference posture. ORODI remains candidate-reverse-link-not-applied. Neither a Goal file nor schema success creates reverse membership or achievement.
7. **Separate selection ownership from semantic ownership.** Each proposal area home owns its input-selection descriptor. The declared lifecycle routes do not take ownership of referenced source meaning. Product, Project coordination, authority integration, ontology integration, implementation and documentation selections remain separately attributable.
8. **Keep shared dependencies referenced.** Source/component bindings are pinned, not runtime installations or caches. Legacy `craft/impl`, `craft/formalization` and `RUNTIME.json` consumers remain in place. No `workspaces/` folder is created.
9. **Bound local variation.** Context-budget, operator-note and a runtime-selection reference are allowed here. They describe candidate configuration and exercise profile evolution; no live runtime behavior is changed. Semantic overrides are prohibited. Recursion depth is one, ending at this package and one pilot profile.
10. **Do not invent global connections.** The native Governed Model carrier requires a relation-role declaration. This model references a candidate Decision representation of the actual conversation authoring request; its subject is this model, and its effect is candidate authoring only. It grants no admission or adoption. No global Typed Relation is materialized. Manifest nesting uses the explicitly local label `local:package-home:contains` for this renderer/validator's structural membership. Global endpoint/kind review remains separate before promotion.
11. **Keep modeled adoption proposed.** Binding state stays proposed and actual adoption outcome remains null, including in the temporary successor fixture. The fixture's next model revision is synthetic and is never published as a real Lab release.

12. **Share operations by default.** The explicit user correction removes any per-workspace runtime requirement. Shared capabilities operate in an explicit workspace/Project/scope/revision context. Workspace state can use a common backend without merging identity or ownership. Behavior specialization may run on the shared runtime; dedicated execution is an independent explicit choice. The candidate Craft selection has no live runtime target. See [shared-runtime model](SHARED-RUNTIME.md).
