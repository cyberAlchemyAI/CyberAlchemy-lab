# Creation and upgrade validation scenario

Scope: executable **candidate-profile fixture**, not a native Craft installation or real workspace adoption.

## Inputs

- The actual proposed Craft workspace, model and binding records.
- Current admitted carrier schemas and descriptor digests selected by the existing registry.
- Exact hashes/lengths of the bounded current-source anchor selection.
- Explicit Project/Product reconciliation and original Goal membership postures.

## Executed positive path

1. Validate native carriers, local profile shape, owner/identity boundaries and exact source selections.
2. Create generation 1 in a fresh temporary directory, containing the actual candidate profile bytes, and publish a local fixture HEAD through atomic rename.
3. Prepare a synthetic compatible model revision and local profile successor. Preserve workspace, Project, Product, Goals, source selections and area identities. Create a different binding identity for the changed model/local endpoint tuple.
4. Require the exact generation-1 preimage and an explicit successor-model reference. Keep adoption proposed and authority effect none.
5. Publish generation 2 without changing generation 1. Launch a separate Python reader process and compare the selected profile bytes.
6. Record and read a two-generation journal with predecessor/successor binding references. Verify predecessor bytes remain exact.
7. Restore the retained generation-1 reader. This fixture declares no irreversible data migration, so this narrow rollback is valid. It does not establish rollback of arbitrary runtime or external effects.
8. Remove all temporary state. Recheck source currentness before reporting success.

## Rejection cases

The validator exercises missing areas; identity collapse; wrong parent revision; collapsed parent/local authority; semantic overrides; premature adoption; shared-runtime copying; unsupported full-source-closure claims; Goal membership inflation; candidate Product promotion; use of the duplicate Project carrier; unbounded recursion; invented owner assignments; unqualified global relations; changed source bytes; a divergent duplicate repinned by a caller; unsafe paths; redispatch with unresolved effects; stale preimages; identity changes during upgrade; reuse of a binding for changed endpoints; and duplicate package membership.

Expected refusal codes and actual results are in the generated validation receipt. Failures are retained as failures; the validator does not refresh source pins or repair original files to make checks pass.

## Shared-runtime reference fixture

The pure resolver checks two workspace scopes using one synthetic shared target, a workspace specialization on that same target, and an optional dedicated target with inherited behavior. Eleven refusal cases cover context mismatch, stale revisions, missing targets, incompatible model versions, foreign specialization/dedicated scope and unauthorized configuration fields. It creates no installations or native effects. Namespace references are configuration evidence, not live storage-isolation qualification.

## Still required for actual operation

An admitted/selected model and local owner outcome; a qualified full functional/source/environment closure; actual shared-runtime dispatch and host permission/state-scope enforcement (or dedicated integration when explicitly selected); live persisted-state migration and interruption handling; native context/replay checks; retained-reader/data compatibility; and external-consumer transition where relocation is selected. Those are distinct later Work, not outcomes inferred from this fixture.
