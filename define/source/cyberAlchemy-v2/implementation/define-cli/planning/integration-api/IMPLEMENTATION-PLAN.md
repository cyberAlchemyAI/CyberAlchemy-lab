# Define Integration API Implementation Plan

## Objective

Deliver the design in [DESIGN.md](DESIGN.md) through the evidence-gated layers
in [IMPLEMENTATION-LAYERING.md](IMPLEMENTATION-LAYERING.md), beginning with L0.
This plan grants no implementation, admission, activation, publication,
release, deployment, or external-effect authority.

## Delivery Boundary

Included across the full plan:

- a generic compiled Alch decision layer for stage transitions;
- a closed static stage-registry contract;
- a typed ontology-stage facade over ARE Module Port mechanics;
- a stable Define Client API;
- Product and Business ontology adapters;
- a third-adapter extensibility witness; and
- a typed candidate handoff to one Plan consumer.

Excluded:

- filesystem discovery, plugin installation, provider priority, semver ranges,
  hot reload, untrusted code, remote transport, effects, credentials, automatic
  admission, canonical promotion, publication, release, and deployment.

## L0 Implementation Detail

Inputs:

- one exact stage descriptor set;
- one immutable Module Port instance;
- frozen work/stage state;
- zero or one exact prerequisite receipt per declared dependency; and
- explicit user response/confirmation facts.

Ordered rules:

1. Validate and canonicalize descriptors.
2. Reject duplicate stage IDs/types/capability bindings, missing dependencies,
   cycles, and authority-bearing material.
3. Sort the dependency graph and compute its digest independently of input order.
4. Resolve the selected entry stage and only its prerequisite closure.
5. Invoke each stage operation through the typed facade and exact capability ID.
6. Keep unavailable, blocked, not-ready, deferred, and invalid distinct.
7. Permit materialization only after generic and adapter readiness pass.
8. Permit export only after exact-byte user confirmation and adapter validation.
9. Seal the candidate and handoff receipt over graph, module-set, dependency,
   confirmation, input, and output digests.

Failure modes include unknown stage, unavailable adapter, invalid provider
output, exception, stale predecessor receipt, revision conflict, missing
confirmation, semantic-quality block, and effect smuggling. All return stable
reason codes and `authority_effect: none`.

## Validation Strategy

Every delivery slice runs focused tests twice and then the complete Define test
suite. Alch-bearing tasks also rebuild from source and compare generated bytes.

Required semantic checks remain explicit:

- **semantic grounding:** every candidate assertion traces to exact user evidence;
- **non-collapse:** distinct terms cannot silently normalize to one meaning;
- **orthogonality:** classification axes are independent or carry named coupling;
- **adapter orthogonality:** one optional branch cannot block an unrelated branch;
- **authority non-collapse:** readiness, validity, confirmation, admission, and
  activation remain distinct; and
- **replay:** identical source, graph, state, and module set reproduce the same result.

Suggested L0 verification surfaces:

```bash
node --test implementation/define-cli/test/integration/*.test.mjs
node implementation/define-cli/scripts/verify-alch-runtime.mjs
cd implementation/define-cli && npm test
```

The exact commands must be confirmed against the files created in T0. For any
Rust/C/C++ verification, use the repository `tools/toolchain/run` launcher.

## Gates And Blockers

- `G0`: owner accepts the L0 descriptor and receipt shapes before runtime mutation.
- `G1`: L0 evidence passes before current CLI/chat code is migrated.
- `G2`: Client API parity passes before a real ontology adapter is added.
- `G3`: Product candidate semantics and owner boundaries are selected before T2.
- `G4`: Plan consumer schema is named before T4.
- Goals validation is currently blocked; these artifacts remain candidate and
  cannot be registered as admitted execution state.
- The installed Invoke skill's referenced `plan.md` mode contract is absent.
  This plan applies the available root gates and templates but must not claim a
  complete Invoke plan-mode pass until that package gap is repaired.

## Completion Evidence

Full-plan completion requires:

- L0–L4 exit evidence;
- no ontology-name branches in Define core;
- a zero-adapter non-regression result;
- byte-identical Alch regeneration;
- exact source/manifest/module-set/stage-graph receipts;
- a third ontology added without a Define-core edit; and
- one typed Plan-consumer acceptance test that preserves candidate/no-effect posture.
