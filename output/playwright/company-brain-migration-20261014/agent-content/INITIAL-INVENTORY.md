## Start here primer: semantic coverage to confirm before removing sections

All the following already have substantive explanation in the baseline technicalguide, incident walkthrough, Craft article, reference definitions, or existing company-brain article. Preserve the destinations to those owners; there is no need to reinsert the whole primer into a second page.

- `#organize-knowledge`: meaning/purpose/performed work/possible change connect in persistent records; Northstar is fictional. Existing company-brain opening and incident cover this.
- `#definitions-first`: accepted **exact version**, accountable owner's **declared purpose and scope**; identifier completeness is fixed-account/filter/snapshot **coverage**, with **value accuracy and data-access permission separate**. Technicalguide opening incident and Definition formal record cover these details.
- Definition states meaning/boundaries; Artifact Type contract includes **meaning bindings, format and validation**; Artifact is **identifiable, typed and versioned**. These belong at the existing formal entries and technicalguide `#records`.
- Ontology View retains selected subject/relationship identities and **dependent sources**. Technicalguide records/views plus formal Ontology View cover this.
- `#three-questions`: meaning authority is separate from action permission; provenance lists snapshot/account/filters/output/method/result; definition/code/incident have their **own states and change requirements**; evidence supports scoped conclusion, permission governs action, transition records resulting state. Technicalguide governance/evidence/change sections already own these.
- `#purpose-and-work`: Intent Resolution records response and success assessment; Product Capability names promised outcome and Implementation realizes it; Project coordinates repair; Goal requires outcome/evidence; Work names inputs/constraints/results; Assignment identifies participation while permission is separate authority/delegation. Technicalguide `#purpose` and `#agent` provide richer examples. Avoid replacing the whole set with only “Intent gives purpose.”
- `#agent-continuity`: both views identify **source versions, limits and refresh conditions**; Project State persists histories/connections as well as saved records; machine-agent instance ends with session; surviving comparison permits later cause investigation; use/benefit evidence for lessons. Technicalguide `#agent`, practical resume guide and article `#agent-memory` already own these.
- `#craft-in-the-lab`: Rule condition / Calculation derived value / Query retrieval / Operation state change; capacity accepts **strictly below**, rejects equality; generated code and checks may be Work outputs; acceptance/deployment follow own authority routes. Technicalguide `#purpose` has all four roles and strict inequality; Craft article has correction from historical Operation fixture to pure Calculation, explicit no mutation, and authority distinction. Preserve these bodies exactly.
