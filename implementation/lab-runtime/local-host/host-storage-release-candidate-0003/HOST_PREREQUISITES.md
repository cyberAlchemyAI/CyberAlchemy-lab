# WSL host prerequisites outside the fixed storage transaction

This candidate has two bounded filesystem transactions: three root-owned code-install entries, then seven storage entries. The Docker tests prove their local mechanics on disposable tmpfs. They do not establish an independent WSL authorization, a receipt-install effect, or a zero-unselected-effect WSL execution.

1. **Independent decision and receipt custody.** A distinct reviewer must inspect the final frozen v3 hashes and a fresh WSL ancestor/mount/ACL/absent-name preimage, issue an explicit PASS for *this* one-shot storage scope, and identify themselves. The present v2 independent verdict is HOLD and cannot be copied into a PASS receipt. The reviewer-approved receipt bytes must bind the v3 release and runtime-pin SHA-256 values, exact target and fresh preimage. Its root-owned `0400`, nlink-one installation at `/usr/local/libexec/cal-host-storage-release-0003/review-receipt.json` requires its own exclusive, no-follow, held-parent installer or separately reviewed administrator transaction. No such receipt installer is part of v3, and the receipt is currently absent. The v3 parser rejects missing/malformed reviewer fields; it cannot prove who authored a syntactically valid field.
2. **Installer launch and ambient host effects.** The README's held-FD/hash-pinned stdin launch selects the exact installer bytes. Inside that program, the interpreter SHA-256, isolated flags/path, 108 Python and ELF file digests and imported module paths are checked before the first package mkdir. Interpreter startup and dynamic-loader execution necessarily precede this in-process check. `sudo -n` may use PAM, audit, journald, timestamp or session state before the root interpreter starts. Those effects are not included in the three-entry code-install manifest. Before WSL execution, a host administrator and reviewer must select whether these ambient changes are admissible, inspect the local sudo/PAM/NSS and logging configuration, record before/after witnesses for the selected auxiliary paths or use an already-qualified privileged executor, and state the resulting claim limit. A no-effect claim for sudo/PAM/startup is unsupported.
3. **Code installation and readback.** After the preceding selections, run the pinned launch exactly once against an absent package name. An independent reader must compare the installed file hashes, owner/modes/nlinks, attached inode chain and ancestor metadata after the installer exits. Any partial/unknown package remains consumed; no reset or retry.
4. **Storage release and post-effect oracle.** Only after a distinct receipt transaction and fresh storage preflight may the root-owned release's one-shot route be considered. The same auxiliary launch accounting applies. An independent WSL reader must then verify the seven entries, record bytes, inode witnesses, ownership, modes, mount and parent metadata, and a hostile service-UID denial on this host. Docker UID denial is not a WSL oracle. No account/unit/cgroup or protected Source8 authority is provided here.

None of these host prerequisites was performed while preparing v3. The selected WSL code and storage names remain absent at the last read-only check. A review of the local sudo/PAM configuration and authorization context is a bounded next step; it is not evidence that the WSL effects occurred.
