## R01 — newly created attempt inode can be replaced and adopted before its first open

`controller.py:243–266` calls `os.mkdir('attempt', dir_fd=parentfd)`, marks the claim consumed, and then calls `os.open('attempt', dir_fd=parentfd)`. It compares the opened descriptor with the **current name**, but never joins it to the inode originally created by `mkdir`. A real-directory replacement in that gap therefore passes the later attachment checks.

In an independent disposable `/tmp/fixture-signed-scope-*` run, I interposed the `os.open('attempt')` call: the original newly created directory was renamed to `detached-original` and another real owner directory took the `attempt` name. The checked controller returned `PROVISIONAL_FIXTURE_SIGNED_SCOPE_EXTERNAL_OS_REVIEW_REQUIRED`; it opened and closed the synthetic Reader, wrote both `consumed.json` and `signed-scope.attestation.json` into the replacement, and bound the attestation to the replacement inode. The original claimed directory remained empty. The same result occurs under normal and `-O` Python. This is a fixture-only race, not a claim that actual private data was read. It directly contradicts the handoff’s claimed attempt/marker identity semantics and its postmarker replacement test’s intended protection.

Required correction: preserve a verifiable identity for the newly created attempt before any pathname reopen can be adopted, retain the original descriptor throughout marker, signed-view and attestation work, and refuse/UNKNOWN on a mismatch before writing or opening the Reader. Add this exact post-`mkdir`/pre-first-open real-directory replacement test in a disjoint successor. State explicitly the cooperative same-UID ceiling: `mkdirat` alone does not return a directory descriptor, so protection against a hostile actor replacing the name before the first identity observation requires a stronger namespace/claim design. Do not treat an attachment to whatever currently has the name as proof of the original claim.
