## Custody and concurrency finding

The Docker command starts one Python entrypoint directly, but **does not exclude a concurrent in-container writer**. `--pids-limit 64` permits additional tasks; `--network none` and read-only image/input mounts do not make `/attempt/tmp`, `/tmp`, or the output bind immutable. The snapshot directory and files are owned by the running UID 1000, which may create another thread/process and may chmod and rewrite an owned 0400 file. Even without a deliberate child in the reviewed code, “one launched entrypoint” is not a daemon-enforced sole-writer guarantee. The entrypoint's anchored copy/readback and cleanup detect many attachment changes, but a same-UID writer can race child pathname validation and removal; the entrypoint handoff itself records that limitation. Its snapshot is therefore a selected local fixture copy, not protected exclusive custody.

Host held-directory FDs, pre/post `st_dev`+`st_ino` checks, full 986-file hashes, and Docker's selected name/image/label/CID establish useful host-side observations. They **do not bind the inode the daemon resolved** for each `src=` path in `docker create`: the CLI sends path strings to a separate daemon, which resolves/mounts them after the host checks. `docker inspect` mount Source/RW fields could corroborate the path and flags, but not alone attest the actual mounted inode or all bytes at cold-open. The stage is under a UID-1000-owned `/tmp` path, and that same host UID can mutate/rename its own tree. The docker-group membership also prevents describing this WSL UID as a restricted adversarial boundary. Read-only input bind blocks writes to that mount from the container; it does not block host-side mutation of the underlying files. The Reader's inside-container rehash, copied snapshot, postclose host rehash, and period checks support an exact-pinned *observed* local run, provided the final release verifies what the daemon mounted and reports UNKNOWN on any mismatch; they do not transform this into protected Source8 qualification.
