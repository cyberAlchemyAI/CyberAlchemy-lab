## Blocking finding R01: one-shot process and terminal evidence are unclosed

The proposed shell command wraps `docker run --rm` in `timeout --signal=TERM --kill-after=10s 180s` but gives the container neither a unique name nor a CID file. A timeout or interrupted Docker client can leave a daemon-side container running with the writable `packages` and `receipts` mounts. `--rm` is not proof that the daemon removed it after client termination. There is no exact container identity to inspect or stop, no bounded daemon-side stop/kill/wait/reap procedure, and no post-exit absence check. The command redirects output with ordinary `>` and `2>`, which can replace existing log files, and does not persist the Docker exit status, timeout reason, output hashes, final directory attachment, or a terminal no-retry/UNKNOWN receipt. An interrupted attempt before `packages/0001` exists has no atomic consumed marker; the handoff's no-retry rule is therefore documentary only. This is a false-PASS/ambiguous-lifetime risk, not a failure of the inert public cut.

**Required correction before dispatch:** freeze a new versioned launcher that atomically reserves a unique attempt and no-replace bounded logs/receipt, gives Docker an exact CID/name, records the child/daemon identity and exit status, enforces the deadline with daemon-side stop then kill, verifies no selected container remains, and publishes PASS only after the package/cold result, output-root attachment/readback, stream bounds and cleanup have been checked. Any timeout, failed verification, or uncertain container state must retain the attempt as UNKNOWN without rerun. Independently test fault and timeout paths without Source effect, then review the exact new command and absent roots/logs again.
