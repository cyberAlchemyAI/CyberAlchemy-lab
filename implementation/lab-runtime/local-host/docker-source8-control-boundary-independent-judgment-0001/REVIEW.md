# Independent judgment: Docker Source8 control boundary

**Verdict: the disposable Docker probe remains PASS; current-family T02/T35 activation remains HOLD.** `vlad_` being in the `docker` group is **not, by itself, an original hard blocker**. It is an administrator-equivalent capability that must be explicitly placed inside the trusted control-plane boundary. The original [T02](../../../../docs/plans/0011-lab-runtime-completion/work-pack/tasks/T02.md) asks for a distinct, current, signed family and correct fixture behavior; [T35](../../../../docs/plans/0011-lab-runtime-completion/work-pack/tasks/T35.md) asks for an actual current-family lifetime. The later [audited custody design](../../../../docs/plans/0011-lab-runtime-completion/runs/0001-execution/acceleration-audit-20261018/design-audit-0001/DESIGN.md) explicitly trusts the administrator/kernel and fixed broker, while excluding untrusted workload peers and arbitrary same-UID holders. It does **not** demand proof that root or a trusted administrator is technically unable to mount a Docker volume. Treating that impossible proof as a gate would overconstrain the original objective.

The [slot review](../docker-source8-slot-independent-review-0001/REVIEW.md) correctly identifies a real mechanism limit: another Docker-capable client can mount the same named volume read-write, and the probe demonstrated that a UID 20001 peer can then create a sibling. A named volume, `0700`, and `flock` do not independently enforce unique writer custody. This does not make a trusted `vlad_` account an adversary. It means Docker API admission and the administrator's operating role must be part of the reviewed deployment, with no untrusted principal able to obtain a competing read-write mount or the service credentials. A current read-only snapshot finds `docker:x:986:vlad_`, `vlad_` in that group, and `/var/run/docker.sock` owned `root:docker` mode `0660`; it is **not** a complete daemon endpoint, privileged-client, process, or future-policy census. UID 20001 is the prospective workload identity, separate from Docker operators; it must have no Docker socket, host mount alias, privileged capability, or route to start a peer with a read-write volume.

The exact minimum current-family evidence is:

1. A selected trust and admission record naming this daemon/socket or other reachable endpoints, `vlad_` as trusted administrator/operator, the reviewed root-owned launcher or operator procedure, all other API-capable principals, and a rule admitting exactly one pinned writer container with the selected volume read-write for the family's lifetime. A new Docker-side policy/broker is one possible implementation, **not an original mandatory product requirement**. If the existing reviewed broker design is retained verbatim, its stricter “interactive user has no credential path” condition conflicts with `vlad_` Docker membership; either enforce that selected design or independently review a Docker-specific alternative with `vlad_` explicitly trusted. Do not silently call the old design satisfied.
2. A fresh family/slot identity and current signed Source/Reader/Mapper/Context scopes; attributable a/b slot and detached-descendant disposition; exact period, image/code and immutable input pins; and a continuous held slot/owner epoch from selection through signing, effects, terminal disposition, and cleanup. These are separate from Docker permissions. Historical expiry and an empty process scan do not release a slot.
3. Actual deployment observations tying the daemon, volume name/label/marker and mount identity, exact writer CID/image/command/mounts, UID/GID 20001, held parent/child and lock descriptors, no writable host aliases, and the final linked output tree to that family. Show the writer is the only admitted read-write mount during the live gap and full run. A point-in-time `docker inspect` or advisory lock is insufficient alone.
4. Under that **installed** admission topology, an independent uncooperative probe attempts the pre-open child replacement and competing sibling creation from every untrusted reachable peer class, including a UID 20001 container without a read-write grant and any nonadministrator Docker client if one exists. Record kernel errors, identities, mount access, time/slot continuity, and post-effect volume/container inventory. A trusted administrator/root capability is an explicit assumption to monitor and invalidate on misuse, not a peer to “deny.”

This judgment removes only an artificial absolute exclusion of `vlad_` from Docker. It does not transform the synthetic probe into a protected producer, authenticate any issuer/grant, prove current exclusive custody, or complete T02/T35. No host effect or private-source read was performed for this review.
