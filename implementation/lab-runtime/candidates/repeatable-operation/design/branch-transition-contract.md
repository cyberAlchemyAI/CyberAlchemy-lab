# C05 candidate successor reconstruction

`prepare_transition` independently replays an externally pinned legacy parent, captures a newly selected source profile and classifies explicitly selected committed results. It produces exact reconstruction postimages and a review plan. Records present in the new baseline are already promoted; identity collisions, historical or withdrawn results, incompatible current schemas and unresolved typed endpoints are conflicts. Explicit exclusions produce no successor records. Any selected carry classified as conflicting or already promoted blocks genesis.

`LocalPolicy` is supplied by a trusted local adapter, with the owner public key, a separate branch identity, exact absolute destination, scope, expiry and the single candidate reconstruction effect. A call body or profile selection cannot supply its own permission. `authorize_transition` signs the exact plan and policy with a separate Ed25519 key outside the repository and both branches, mode 0600. This candidate protocol uses the existing Python JSON encoding and digest; it does not claim RFC 8785 canonicalization.

`apply_transition` holds the parent's existing writer lock in shared mode, verifies the entire parent again, captures and compares the new source cut, checks the exact approval and creates a separate signed genesis. Original baseline bytes remain in the capture. Reconstructed record bytes are explicit new postimages; their provenance names the original committed transaction SHA, digest and JSON selector. Original precommit artifact bytes are unavailable in the legacy format. Old transactions, old signatures and old Decision identities are not copied as successor authority.

All records retain `candidate-reconstructed` posture. Baseline authority remains as captured. No new semantic extension is usable globally merely because its record was carried; extension inspection, semantic admission, repository publication and activation have separate gates. Typed relations must satisfy an existing exact ordered endpoint pair and qualifiers. All categories use their selected current carrier schemas and exact identity selectors; generated runtime consequences are not independently authored transition inputs. Non-relation schema fields are checked structurally; unresolved domain references inside a Work record are not represented as delivery evidence.

Genesis publication is Linux `renameat2(RENAME_NOREPLACE)` through an opened destination-directory capability, after fsync of every file and directory. There is no check-then-overwrite fallback. No previously existing destination is overwritten. A complete signed hidden stage can be verified and published on retry. Unknown or incomplete stages are retained and rejected. After the atomic rename, cold replay verifies the external HEAD, plan, policy, new baseline/profile and original file SHA pins, exact file closure, signature and current schema conformance. Expired permission prevents a new apply; historical cold verification retains the original approval time.

This format provides a candidate genesis and cold reconstruction. General successor transaction append, the artifact handler/API transport and governed workflow/ontology views remain downstream work. Actual operator branch provisioning requires the final R08/A02 scope; isolated fixture stores and test keys are temporary and are never repository artifacts.
